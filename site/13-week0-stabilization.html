13 · WEEK 0 STABILIZATION — 30 ส.ค. 2026

ปิดช่องโหว่ CRITICAL ทั้ง 6 รายการ ภายในวันเดียว

แก้ตามแผนใน หน้า 12 §3 ทุกข้อทดสอบกับระบบจริงก่อน-หลัง ไม่ใช่การคาดการณ์ — สมอ acceptance criteria ที่ตั้งไว้ล่วงหน้าทุกข้อ

ผลรวม smoke test 22/22 invariants + 6/6 security gates ผ่าน ของแถม ยืนยันครั้งแรกว่า edge caching ทำงานจริง (MISS→HIT→HIT→HIT)

§2 รายละเอียดการแก้ — กรองตาม task

T1 · Caddy config ที่หายจากดิสก์FIXED

Container ถือ file handle inode 138459 (1,467 bytes, 3 site blocks) ขณะที่ไฟล์บนดิสก์ถูกแทนที่เป็นคนละไฟล์ (inode 157112, 428 bytes) — config ที่รันอยู่ ไม่มีใน git history เลย ถ้า container ตายก่อนกู้จะหายถาวร

ดึง config จาก container มาเก็บก่อน → เขียนกลับโดยรักษา inode เดิม (cat > ไม่ใช่ sed -i ซึ่งเป็นสาเหตุของปัญหานี้ตั้งแต่แรก) → restart → commit เข้า git

ทดสอบ: เทียบ baseline ก่อน/หลัง restart ทุก endpoint ตรงกัน 100% — https://dvwa.waf-it-kku.online/, SQLi payload, TLS issuer (Let's Encrypt), strict TLS ทั้งหมดผ่าน

T2 · Rule drift custom-123.confFIXED

ทิศทางกลับจากที่คาดตอนวางแผน — ตอนวางแผนเข้าใจว่า production ผิด แต่ความจริงตรงข้าม: git มี @rx test (อันตราย ไม่ anchor จะบล็อกทุก URL ที่มีคำว่า "test") ส่วนเครื่องจริงมี @rx testpj ที่ถูกต้องอยู่แล้วแต่ไม่เคย commit

แก้ไฟล์ใน repo ให้ตรงกับ production แล้ว commit ทั้งสองเครื่อง — ทดสอบ: /latest /contest /testimonials → 404 (ไม่บล็อก) ✅, /testpj → 403 ✅, git diff = 0 ทั้งสองเครื่อง

T3 · กู้ tunnelFIXED (รอบแรก — ทางสำรอง)

Lab node เข้าไม่ถึงตอนนั้น → ใช้ทางสำรอง: ชี้ dvwa.waf-it-kku.online ไปที่ container dvwa ที่รันอยู่บน Main แทน (แก้ 3 บรรทัดใน nginx template, ไม่แตะ juice)

เงื่อนไขคือต้องผ่านพร้อมกัน: / → 200 (origin ไม่ตาย) และ SQLi → 403 (WAF ยังทำงาน) — ผ่านทั้งคู่ ✅ ของแถม: origin กลับมามีชีวิต ทำให้ทดสอบ cache ได้เป็นครั้งแรก: MISS→HIT→HIT→HIT พิสูจน์ edge caching ทำงานจริง

อัปเดต: รอบที่ 2 ย้อนกลับไปใช้ tunnel จริงหลังพบ root cause แท้จริง — ดู หน้า 14

T4 · ปิด Control API จากอินเทอร์เน็ตFIXED

Root cause จริง: ufw ตั้งกฎถูกแล้ว (8070 ALLOW IN 45.154.26.91) แต่ Docker แทรก iptables rule ของตัวเองที่ถูกประเมินก่อน INPUT chain ของ ufw — กฎ ufw จึงไม่มีผลกับ port ที่ container publish เลย

ใส่กฎที่ DOCKER-USER chain (chain ที่ Docker การันตีว่าจะไม่เขียนทับ) แล้ว persist ผ่าน /etc/ufw/after.rules

ทดสอบ 3 มุม: อินเทอร์เน็ต = 000 (บล็อก) / Edge = 200 (rule sync ไม่พัง) / localhost = 200 — ทดสอบ persistence ผ่าน ufw reload แล้วยังเหมือนเดิม, port อื่นไม่กระทบ

T5 · FRP token รั่วสู่สาธารณะFIXED

แก้ที่ต้นเหตุ ไม่ใช่แค่ลบ token: implement endpoint ที่หายไป GET /api/tunnels/config-generator (admin-only, อ่าน token จาก env, validate input เพราะ interpolate เข้า shell command) → เอา fallback ที่มี secret ออกจาก frontend → หมุน token ใหม่ด้วย openssl rand -hex 32 → rebuild frontend

ทดสอบ: token เดิมใน bundle ใหม่ = 0 ครั้ง (เดิม 2), purge token เดิม = 0 ครั้ง (เดิม 1), token ใหม่ในบันเดิล = 0 ครั้งเช่นกัน (ไม่รั่วซ้ำ), endpoint ใหม่คืน 401 เมื่อไม่มี auth — พ่วงแก้ปุ่ม Purge ที่ 422 ตลอดไปด้วย

T6 · SQL InjectionFIXED

ป้องกัน 2 ชั้น: (1) _parse_time_bound() แปลงเป็น datetime object จริง รับเฉพาะ 3 รูปแบบ อย่างอื่นคืน 422 ทันที ใช้กับทั้งค่าจาก request และจาก Gemini เหมือนกัน (2) เปลี่ยนทั้ง 4 query เป็น parameterized query ผ่าน clickhouse-connect

ระหว่างทางพบ bug ซ้อน: outer except Exception จับ HTTPException แล้วแปลง 422 ของเราเป็น 500 พร้อม leak str(e) — แก้เพิ่ม except HTTPException: raise ก่อน handler กว้าง

ทดสอบ 9/9: ช่วงเวลาถูกต้อง → คืนข้อมูลจริง 1,593 รายการ (พิสูจน์ว่าไม่ใช่แค่บล็อกทุกอย่างทิ้ง) / injection 8 รูปแบบ (quote, OR, UNION, DROP, comment, backslash, ที่ end_time, ช่วงกลับด้าน) → ปฏิเสธด้วย 422 หมด

§3 ยังเหลือ

เร่งด่วนกว่าที่เหลือ

Lab node เข้าไม่ได้ตอนนั้น (แก้แล้วในรอบถัดมา — ดูหน้า 14) · เพิ่ม auth ให้ control-api endpoint (/api/sync/bundle, /api/blocklist — ต้อง rebuild image) · เปลี่ยน FRP_ADMIN_PASS จากค่า default

ยังไม่ได้ยืนยัน

Rate limiting ทำงานถูกต้องหรือไม่ — ต้องใช้ load tool จริง (k6) ยิงให้เกิน 50 req/s จริงๆ · Cloudflare Tunnel bypass บน Lab ที่เอกสารเก่าระบุไว้ — ตรวจไม่ได้เพราะตอนนั้นเข้า Lab ไม่ได้ (ยืนยันแล้วว่ามีจริงในหน้า 14)
