WAYFINDER · 28 · SECURITY BOUNDARIES & GAPS — สำรวจสด 6-7 ก.ย. 2026

ทุกขอบเขตความไว้วางใจ + 13 ประเด็นเรียงตามความเร่งด่วน

อะไรทำให้เชื่อได้ และตรวจที่ไหนของทุกจุดในระบบ — ปิดท้ายด้วยสิ่งที่ยังไม่รู้และลำดับการแก้ที่เสนอ ทุกข้อเป็นการรายงาน ยังไม่มีการแก้ไขใดๆ เกิดขึ้น

§1 แผนผังขอบเขตความไว้วางใจ (TB-1 ถึง TB-9)

TB-1 · อินเทอร์เน็ต → Edgeช่องโหว่ยืนยันแล้ว

TLS + limit_req 50rps + ModSecurity — แต่ on-demand TLS อนุมัติทุก domain (ดู §2) และ wildcard DNS ชี้ node เดียว

TB-2 · Edge → Main WAFไม่เข้ารหัส

ไม่มีการพิสูจน์ตัวตนใดๆ — HTTP ธรรมดาข้าม WAN, X-Forwarded-For ไม่ตรวจ trusted proxy

TB-3 · WAF → Tunnel → Originออกแบบดีที่สุด

origin ไม่เปิดพอร์ตขาเข้าเลย — CloudWAF ใช้ HMAC digest + fail-closed; FRP มี legacy token ที่ฝังในซอร์ส

TB-4 · เบราว์เซอร์ → Dashboard APIมีช่องว่าง

JWT + role สดจาก DB (ดี) — แต่ JWT_SECRET_KEY มี default ที่ทำงานต่อได้เงียบๆ

TB-5 · service ↔ service ภายใน Mainยอมรับได้ตาม scope

ไว้ใจตามตำแหน่งเครือข่าย ไม่มี mTLS — นอก scope โปรเจกต์นี้ตาม CLAUDE.md

TB-6 · Application → Data storeRedis ไม่มี auth

ClickHouse/Redis ไม่มี auth จริง — กันด้วย firewall เท่านั้น (ยอมรับตาม scope)

TB-7 · Webhook ขาเข้าไม่ตรวจผู้เรียก

frp-hook และ verify-agent ไม่ตรวจว่าผู้เรียกคือ frps/tunnel จริง — พึ่ง firewall (พอร์ต 8000 ปิดจากอินเทอร์เน็ต) เท่านั้น

TB-8 · tenant ↔ tenantCopilot รั่ว

tenant identity มาจาก origin.admin_user_id เท่านั้น — copilot_chat() ไม่กรอง tenant เลย

TB-9 · input ผู้ใช้ → state ที่เชื่อถือป้องกัน injection ครบ

ClickHouse escape, SecRule escape, DynamoDB expression object, regex ผู้ใช้รันแยกโปรเซส timeout 50ms กัน ReDoS

§2 On-demand TLS — ช่องโหว่ที่ถูกใช้ผิดอยู่จริงตอนนี้

เครื่องask endpointตรวจจริงไหม
Main/api/healthตอบ 200 เสมอ — ไม่ตรวจ
Edge THcdn-edge-node:80/healthzตอบ 200 เสมอ — ไม่ตรวจ
Edge Azure/api/domains/check-ssl-allowedตรวจจริงกับ DynamoDB — ใช้เป็นต้นแบบได้
หลักฐานว่ากำลังถูกใช้ผิดจริง (จาก audit.json และ frps log)

hostname เช่น pochtabank.pay.sberbank.987654321sbermegamarket.<random>.waf-it-kku.online, youla.sbermegamarket..., blablacar... วิ่งเข้ามาต่อเนื่อง — รูปแบบ subdomain ที่ใช้ทำเพจปลอมของบริการรัสเซีย ปัจจุบันได้ 502/504 เพราะไม่มี tunnel รองรับ แต่ cert ถูกออกให้ไปแล้วจริง

§3 13 ประเด็นความปลอดภัย เรียงตามความเร่งด่วน

  1. 01
    PAT ของ GitHub ฝังใน git remote บน Main

    ส่งผลนอกขอบเขตเครื่อง — ควรเพิกถอนทันที

  2. 02
    on-demand TLS อนุมัติทุก domain + wildcard DNS

    โดเมนโปรเจกต์ถูกใช้ทำเพจปลอมอยู่จริง

  3. 03
    Copilot รั่วข้อมูลข้ามผู้เช่า

    รวมถึง IP ผู้โจมตี และส่งต่อออกไป Gemini โดยไม่ mask

  4. 04
    legacy static token ของ FRP ฝังในซอร์ส

    ไม่ผูกกับ domain — ผ่านได้ทุก domain ที่ไม่ reserved

  5. 05
    JWT_SECRET_KEY มีค่า default ที่ทำงานต่อได้เงียบๆ

    ถ้า env ไม่ถูกโหลด ปลอม JWT ได้ทุกใบ

  6. 06
    /api/auth/tunnel/verify ใช้ origin id เป็นความลับ

    waf_token ไม่ใช่ความลับจริง — ดูเหมือนโค้ดรุ่นเก่าที่ค้างอยู่

  7. 07
    tenant isolation ของ log ใช้การเทียบสตริง

    ผลลัพธ์ปนกันได้ระหว่างผู้เช่า

  8. 08
    X-Forwarded-For ถูกเชื่อโดยไม่ตรวจ trusted proxy

    ปลอม IP หลบ rate limit ได้

  9. 09
    log_forward เก็บ raw ทั้งก้อนลง DynamoDB โดยไม่ mask PII

    ประเด็น PDPA

  10. 10
    รหัสผ่าน ClickHouse / CONTROL_TOKEN อยู่ใน git

    อยู่ใน history ถาวร

  11. 11
    Redis ไม่มีรหัสผ่าน

    นอก scope ตาม CLAUDE.md — กันด้วย firewall

  12. 12
    Edge→Main เป็น HTTP ไม่เข้ารหัสข้าม WAN

    INFERRED จาก config

  13. 13
    Azure edge ไม่ได้รับ rule sync

    ถ้าเปิดใช้จริงจะบังคับ rule ไม่ครบ — ยังไม่กระทบเพราะไม่มีทราฟฟิก

ทุกข้อเป็น การรายงาน ไม่มีการแก้ไขใดๆ เกิดขึ้นระหว่างการสำรวจ — การแก้แต่ละข้อเป็นการเปลี่ยนแปลงระบบ ต้องอธิบายและขออนุมัติก่อนทุกครั้ง

§4 สิ่งที่ยืนยันแล้วว่า "ไม่มี" (ปิดประเด็นได้)

  • Kubernetes — ไม่มีบนเครื่องใดเลย ใช้ Docker Compose + systemd ล้วน
  • message queue (Kafka/RabbitMQ/SQS/Celery) — ไม่มี ใช้ asyncio task + dict ในหน่วยความจำ
  • Cloudflare Tunnel ที่ยังทำงาน — ไม่มี process, ไม่มี config, unit disabled ทั้งคู่
  • การที่ ML สั่ง block เอง — ไม่มี code path ใดที่ ML ทำให้เกิด deny โดยตรง
  • /api/cdn/logs/ingest ในโค้ดที่ deploy — ไม่มี (แต่ edge forwarder ยังยิงไปอยู่)
  • cron job ของโปรเจกต์บน Main — ไม่มี

§5 ยังไม่รู้ — ต้องการหลักฐานเพิ่ม

ขอบเขตสิทธิ์ AWS IAM key

ยังไม่ได้ตรวจ policy ที่ผูกกับ access key — ถ้าสิทธิ์กว้าง การเจาะ backend ได้จะกระทบทรัพยากร AWS นอกเหนือจาก 11 ตารางนี้

พอร์ต 8080 เปิดถึงจากอินเทอร์เน็ตไหม

docker-proxy bind 0.0.0.0:8080 แต่ INPUT policy DROP — Docker chain อาจข้าม INPUT ได้ ยังไม่ได้ทดสอบแยกจากภายนอก

คุณสมบัติ cookie access_token

ยังไม่ได้ยืนยันว่ามี httponly/secure/samesite ครบหรือไม่ — กระทบความเสี่ยง XSS/CSRF โดยตรง

ที่มาการลบ access.json

ยืนยันได้ว่าถูกลบตั้งแต่ 1 ก.ย. 10:16 แต่ไม่รู้ว่าใครลบด้วยเครื่องมืออะไร

§6 ลำดับการแก้ที่แนะนำ (ยังไม่ได้ลงมือ — ต้องขออนุมัติทีละข้อ)

  1. ขั้นที่ 0 — กู้ให้ใช้งานได้ก่อน

    ย้าย save_hybrid_log() ไป run_in_executor/asyncio.to_thread · สั่ง nginx -s reopen แล้วตั้ง logrotate

  2. ขั้นที่ 1 — ปิดช่องที่ถูกใช้ผิดอยู่จริง

    เพิกถอน GitHub PAT · เปลี่ยน on_demand_tls ask ให้ตรวจ DynamoDB เหมือน Azure edge · เชื่อม FRP กลับ (ระวังอย่าแตะ vhost ของ vampi)

  3. ขั้นที่ 2 — ความถูกต้องของข้อมูล

    เพิ่ม/แก้ endpoint /api/cdn/logs/ingest · ทำ log rotation · ปิดรูรั่ว tenant ของ Copilot

  4. ขั้นที่ 3 — เก็บกวาดก่อนนำเสนอ

    ลบ custom rule ทดสอบ · เก็บไฟล์ .bak-* ออก · บันทึกตัวเลข ML จริง (accuracy 0.8047 / recall 0.6226) แทนตัวเลขที่ README เคยอ้าง

เลื่อนไว้ก่อนตาม CLAUDE.md — นอก scope โปรเจกต์จบ

mTLS ระหว่าง service, auth บน Redis/ClickHouse, secret management เต็มรูป · ปรับจูน ML ให้ recall สูงขึ้น · ทำ CDN ให้ครบ (GeoDNS, purge API, multi-node failover)
