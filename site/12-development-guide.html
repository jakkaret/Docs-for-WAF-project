12 · DEVELOPMENT GUIDE — แผนถึงวันส่งโปรเจกต์

จากปัญหาที่ตรวจเจอ สู่แผน 5 สัปดาห์ที่ลงมือได้จริง

สร้างต่อจากผล System Audit — ไม่ใช่ wishlist แต่เป็นลำดับงานที่ผ่านเกณฑ์ชัดเจน พร้อม task card รายละเอียด acceptance criteria และกฎตัดสินใจล่วงหน้าเผื่อเวลาไม่พอ

กรอบเวลา ~1 เดือน นับจาก 29 ส.ค. 2026 ระดับงาน demo-grade เน้น functional correctness ไม่เน้น scale

§1 เกณฑ์จัดลำดับงาน

  1. ระเบิดเวลาก่อนเสมอ

    สิ่งที่ไม่แตะแล้ววันหนึ่งจะระเบิดเองตอนใกล้สอบ (เช่น Caddy config ที่หายจากดิสก์) — ต้นทุนต่ำ ความเสี่ยงสูง

  2. ฐานที่งานอื่นต้องยืนอยู่บน

    ถ้าไม่มีสิ่งนี้ งานถัดไปทำไปก็ไม่มีความหมาย เช่น tunnel ตาย = ไม่มี traffic จริงให้ ML อธิบาย

  3. คุณค่าต่อ thesis

    ตอบ pain point จริงที่มี evidence รองรับ และเป็นสิ่งที่ป้องกันได้ตอน defense

  4. ต้นทุนต่อผลลัพธ์

    งานที่ AI ช่วยเร่งได้ (เขียนโค้ด) มาก่อนงานที่เร่งไม่ได้ (รอ DNS propagate, เช่า VPS, รอ feedback อาจารย์)

สิ่งที่ไม่ใช้เป็นเกณฑ์

ความสมบูรณ์แบบเชิง production (secrets management เต็มรูป, mTLS, HA) — เก็บไว้ทำเวอร์ชัน portfolio หลังสอบจบ · การเพิ่ม scale — ไม่ใช่เป้าหมายโปรเจกต์นี้ · ML accuracy tuning — ตั้งใจเลื่อนไปหลังสอบจบ

§2 แผน 5 สัปดาห์

สัปดาห์ 0 (2-3 วัน)   STABILIZE   ปลดชนวนระเบิดเวลา + กู้ tunnel
สัปดาห์ 1              FOUNDATION  safety net (test/CI) + เริ่ม explainability
สัปดาห์ 2              CORE        explainability ครบ + self-tuning proposal
สัปดาห์ 3              STRETCH     CDN จริง (ถ้าเหลือเวลา) หรือประกาศตัดอย่างเป็นทางการ
สัปดาห์ 4              CLOSE-OUT   regression เต็มระบบ + เอกสาร + เตรียม defense
เปลี่ยนจากแผนเดิมใน Docs/10: "ปิด bypass tunnel" → "กู้ tunnel ให้กลับมาทำงาน" เพราะผลตรวจพบว่า tunnel ไม่ได้ถูก bypass แต่ตายสนิท (FRP client = 0) — คนละปัญหากับที่เข้าใจตอนวางแผนแรก

สัปดาห์ 2 (CORE) คือส่วนที่ต้องรักษาไว้ให้ได้ไม่ว่าเกิดอะไรขึ้น — ถ้าเวลาเหลือน้อยให้ตัดงานอื่นทิ้งแล้วทำส่วนนี้ให้จบ

§3 Task Cards — กรองตามสัปดาห์

14 งาน แบ่งเป็น 4 กลุ่มความเร่งด่วน คลิกป้ายเพื่อกรอง

T1 · ปลดชนวน Caddy config15 นาที

เขียนไฟล์บน host ให้ตรงกับที่ container ใช้จริง ด้วยวิธีที่ไม่เปลี่ยน inode (cat > file ไม่ใช่ sed -i) แล้ว commit เข้า git — ตรวจสำเร็จ: stat inode ตรงกัน + restart แล้วทุก subdomain ยังตอบ 200

T2 · แก้ rule drift custom-123.conf10 นาที

แก้ git ให้ตรงกับ prod (@rx testpj ไม่ใช่ @rx test) — พิจารณาลบทิ้งไปเลยเพราะเป็นแค่ smoke test rule ID นอกช่วง user range ด้วย

T3 · กู้ tunnel ให้กลับมาทำงาน2–6 ชม. (ไม่แน่นอน)

วินิจฉัยตามลำดับ: Lab node ยังมีชีวิตไหม (ต้องหา SSH key) → ถ้าตายจริง ใช้ dvwa container บน Main เป็น origin ชั่วคราว → ถ้า Lab กลับมาได้ ค่อย start frpc ใหม่ ตรวจสำเร็จต้องผ่านพร้อมกัน: เว็บทดสอบตอบ 200 และ payload โจมตียังโดน 403 — งานนี้ AI ช่วยเร่งได้น้อยที่สุด เผื่อเวลาไว้เยอะ

T4 · ปิด Control API จากอินเทอร์เน็ต30 นาที

แนะนำแก้ที่ต้นเหตุก่อน: เพิ่ม auth ให้ GET /api/sync/bundle และ /api/blocklist (ปัจจุบันไม่เช็ค token เลย) แล้วค่อยผูก port ให้เห็นเฉพาะ Edge เสริม — เป็น cross-cutting change ต้องทดสอบว่า rule sync ยังทำงานหลังแก้

T5 · หมุน FRP token + เอาออกจาก frontend1 ชม.

เปลี่ยน token ฝั่ง frps.toml + ลบ fallback ที่ hardcode ไว้ใน Tunnels.tsx (ค่า token จริงไม่แสดงในเอกสารนี้ — ดูตำแหน่งบรรทัดที่ หน้า 11 §4) วิธีที่ถูกต้องเชิงออกแบบ: implement GET /tunnels/config-generator (admin-only) ให้คืน token จาก server แทนฝังใน bundle — ตรวจสำเร็จ: grep JS bundle หา token เก่าแล้วต้องได้ 0 ผลลัพธ์

T6 · แก้ SQL Injection45 นาที

เปลี่ยน ai_summary.py จากต่อ string เป็น parameterized query (clickhouse-connect รองรับอยู่แล้ว) แก้พร้อมกันทุกจุดที่ escape แค่ backslash — เพิ่ม validation ที่ origin.label ด้วยเพราะไหลเข้า SQL ผ่าน tenant filter

T7 · สร้าง tests/ จริง + แก้ CIสัปดาห์ 1

ทดสอบ 5 ไฟล์เดิมอยู่หลัง if __name__=="__main__" pytest เก็บไม่ได้เลย + CI ใช้ || echo กลืน exit code ทุกชนิด — ต้องลบทิ้ง และทำให้ CI รันบน branch backend ด้วย (ตอนนี้รันแค่ main/develop) ชุดแรกที่ควรมี: auth flow, RBAC, tenant isolation, SQLi guard (ยืนยัน T6), rules CRUD

T8 · Smoke test suiteสัปดาห์ 1

script ยิง ~20 endpoint หลักก่อน/หลังการแก้ที่กระทบหลายส่วน (ตามข้อตกลง cross-cutting change ต้อง regression) ไม่ต้องเป็น k6 เต็มรูป bash/python พอสำหรับ demo scope

T9 · Feature attribution pipelineแกนของ thesis

ใช้ shap.TreeExplainer กับโมเดล Random Forest ที่ train ไว้แล้ว (ไม่ต้อง retrain) ขยาย /predict ให้คืนน้ำหนักรายฟีเจอร์ — ข้อจำกัด: nginx log ไม่บันทึก body ดังนั้นอธิบายจาก log ย้อนหลังได้แค่ URI+method ต่างจากตอน train

T10 · แปล attribution เป็นภาษาไทยสัปดาห์ 2

ขยาย gemini_service.explain_attack() ที่มี cache + fallback + model failover 4 ชั้นอยู่แล้ว — ระวัง: Gemini output ห้ามไหลเข้า SQL/shell ตรงๆ (บทเรียนจาก T6)

T11 · แสดงผลในหน้าเว็บสัปดาห์ 2

แนะนำ mount origins_domains_router (แก้ 1 บรรทัดใน main.py) เพราะแก้หน้า Traffic Logs ที่ว่างถาวรไปในตัว — เป็น cross-cutting change ต้องรัน smoke test ก่อน-หลัง พ่วงแก้ optional-chaining ที่ MLRules.tsx/MLAnalyst.tsx ที่ทำให้แอป crash ได้

T12 · Self-tuning threshold proposalสัปดาห์ 2

ส่วนใหญ่ reuse ได้หมด (settings service, ml_rule_service, approve/reject UI มีอยู่แล้ว) สิ่งที่สร้างใหม่จริงคือ logic วิเคราะห์ block rate แล้วเสนอ threshold พร้อมเหตุผลตรวจสอบได้ — ต้องมีคนอนุมัติเสมอ เพราะปรับเองอัตโนมัติเสี่ยง data poisoning (เรียนรู้ผิดว่า attack traffic ถี่ๆ คือปกติ) เป็นการตัดสินใจเชิงออกแบบ ไม่ใช่ข้อจำกัดทางเทคนิค

T13 · แก้ตัวเลข ML ให้ตรงความจริงสัปดาห์ 4

แก้ทุกจุดที่เขียน 93.40%/0.9895 ให้เป็น 80.47%/0.8847 ที่วัดได้จริง — ml/presentation_eval.html ใช้ตัวเลขถูกอยู่แล้ว ใช้เป็นต้นแบบ ตัวเลขต่ำแต่ซื่อสัตย์ดีกว่าตัวเลขสวยที่ตรวจสอบแล้วไม่ตรง

T14 · เอกสาร privacy / PDPAสัปดาห์ 4

ยอมรับตรงๆ ว่ายังไม่ mask ก่อน ingest แม้จะมี pii_masker.py เขียนรอไว้แล้ว ระบุเป็น future work พร้อมชี้ว่า data residency ทำได้จริง (host ในไทยทั้งหมด ยกเว้น Gemini API call ซึ่งต้องระบุตรงๆ ว่าเป็นข้อยกเว้น)

§4 ทางเลือกสัปดาห์ 3 — CDN จริง หรือตัดอย่างเป็นทางการ

ทางเลือก A — ทำ CDN ให้จริง

ถ้าสัปดาห์ 0–2 เสร็จเร็วกว่าแผน: เช่า VPS ต่างประเทศ 1 เครื่อง deploy edge node ที่ 2 — ไม่ต้องครบ 3 region แค่ 2 node ก็พิสูจน์ว่าสถาปัตยกรรมทำงานจริง ⚠️ ต้องรู้ก่อน: GeoDNS ปัจจุบันแมป region ด้วย CIDR hardcode ไม่ใช่ GeoIP — ถ้าจะให้ geo-routing ทำงานจริงต้องเปลี่ยนก่อน

ทางเลือก B — ตัดอย่างเป็นทางการ

ถ้าเวลาไม่พอ: เขียนเอกสาร 1 หน้าระบุตรงๆ ว่าผ่าน 2 จาก 4 องค์ประกอบ CDN (caching ✅, centralized sync ✅, multi-PoP ❌, geo-routing ❌) — นี่ไม่ใช่ความล้มเหลว เป็นการตัดสินใจที่มีเหตุผลรองรับ

เกณฑ์ตัดสิน

ถึงวันจันทร์สัปดาห์ 3 แล้วงานสัปดาห์ 2 ยังไม่ครบ → เลือก B ทันที อย่ายื้อ

§5 กฎตัดสินใจเมื่อเวลาไม่พอ

เขียนไว้ล่วงหน้าเพื่อไม่ต้องตัดสินใจตอนกดดัน

สถานการณ์ทำอะไร
สัปดาห์ 0 ยืดเกิน 4 วัน (มักเป็นเพราะ T3)ใช้ทางสำรอง: origin เป็น dvwa บน Main แล้วเดินหน้าต่อ อย่าติดอยู่กับการกู้ Lab
จันทร์สัปดาห์ 3 แล้วสัปดาห์ 2 ยังไม่ครบตัด CDN ทันที (เลือก B) ไม่ต้องคิด
สัปดาห์ 3 แล้ว T12 ยังไม่เสร็จส่งแค่ T9+T10+T11 (explainability ล้วน) ก็เป็น thesis ที่สมบูรณ์ได้ — self-tuning เป็นส่วนขยาย
เจอบั๊กใหม่ระหว่างทางถ้าไม่บล็อกงานที่ทำอยู่ → จดลง Docs/11 ไม่ต้องแก้ทันที
อยากแก้ ML accuracyอย่า — เลื่อนหลังสอบจบ ยกเว้น wire entropy feature ที่มีอยู่แล้ว (~1 ชม.) ถ้าเหลือเวลาจริงๆ
อยากทำ production hardening (secrets, mTLS, auth บน DB)อย่า — เป็น scope portfolio หลังสอบจบ ยกเว้นส่วนที่อยู่ใน T4/T5/T6 ซึ่งเป็นระดับ critical

§6 คำตอบเตรียมไว้สำหรับอาจารย์

"นี่มันแค่ WAF วางบน server ไม่ใช่ CDN"

ผ่าน 2 ใน 4 องค์ประกอบจริงและพิสูจน์ได้ (caching + centralized sync) อีก 2 ข้อออกแบบ/ทดสอบครบแล้วแต่ยังไม่ deploy เพราะจัดลำดับความสำคัญไปที่ฟีเจอร์หลัก — ดูรายละเอียดที่ หน้า 10

"ML แม่นแค่ไหน"

80.47% accuracy, attack precision 98.39% แต่ recall 62.26% — ตั้งใจให้ precision สูงเพื่อลด false positive และไม่ได้บล็อกเดี่ยว ทำงานคู่กับ Rule Engine

"ML บล็อกเองได้ไหม"

ไม่ได้ — เป็นการตัดสินใจเชิงออกแบบ ไม่ใช่ข้อจำกัด เหตุผลคือความเสี่ยง data poisoning และ recall ที่ยังไม่สูงพอ ทุกกฎที่ ML เสนอต้องผ่านคนอนุมัติ

"AI ในระบบนี้ทำอะไรบ้าง"

3 ชั้นแยกกันชัดเจน: Rule Engine (deterministic, บล็อกจริง) → ML (ให้คะแนน+เสนอกฎ ไม่บล็อก) → LLM (แปลผลเป็นภาษาไทย ไม่ตัดสินใจ)

"ใช้กับเว็บจริงได้เลยไหม"

ยังไม่ได้ และรู้ว่าเพราะอะไร — รายการตรวจสอบครบใน หน้า 11 (secrets management, mTLS, HA, retention policy) ระบุเป็น future work

"ข้อมูลผู้ใช้ปลอดภัยไหม / PDPA"

ยอมรับตรงๆ ว่ายังไม่มี masking/retention ตอน ingest ระบุเป็น future work พร้อมชี้ว่า data residency ทำได้จริงแล้ว (ยกเว้น Gemini API call)

§7 สิ่งที่ตั้งใจไม่ทำในแผนนี้

  • ML retraining / เพิ่ม accuracy — ตกลงเลื่อนแล้ว ไม่ใช่ novelty ของโปรเจกต์นี้
  • Secrets management (vault), mTLS, HA — production hardening ไม่ใช่ scope demo → โปรเจกต์ portfolio หลังสอบจบ
  • Kubernetes, Terraform — เกินความจำเป็นสำหรับ 3 VPS
  • MISP/OpenCTI, Wazuh, ELK เต็มระบบ — ซ้ำซ้อนกับของที่มีอยู่แล้ว
  • แก้ dead code 14 รายการ — ไม่กระทบผู้ใช้ จดไว้เฉยๆ
  • BOLA Guard ให้ enforce จริง — เขียนดีแต่ไม่ได้ wire เป็นงานใหญ่ พูดถึงใน thesis ได้ว่าออกแบบไว้แล้ว
