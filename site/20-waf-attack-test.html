20 · WAF ATTACK TEST — 4 ก.ย. 2026

ยิงจริง 20 payload เข้า WAF — บล็อกได้ 15 เหลือช่องว่าง 5 จุดที่ต้องปิด

ทดสอบ juice.waf-it-kku.online (OWASP Juice Shop หลัง WAF จริง) ด้วย payload โจมตีจริงตาม OWASP Top 10 — ยิงตรงเข้า endpoint จริง อ่าน HTTP status และ response body จริง ไม่ได้จำลอง

ผลรวม บล็อก 15/20 (75%) · baseline 2/2 ไม่ false-positive บล็อกครบ 100% SQLi ตัวรุนแรง · XSS · SSRF · Path Traversal

§1 สรุปผล

20payload ที่ยิงจริง
15บล็อกด้วย 403
5ผ่าน WAF (detection gap)
2/2baseline ปกติ ไม่โดนบล็อกผิด
ยืนยันว่าคนบล็อกคือ ModSecurity จริง ไม่ใช่ origin

response body ของทุก request ที่ได้ 403 คือหน้า 403 Forbidden - WAF Protection ที่เรา custom ไว้เอง — ไม่ใช่ 403 ที่แอป Juice Shop ตอบกลับมา แปลว่าการบล็อกเกิดที่ชั้น WAF ตามที่ออกแบบ

ขอบเขตที่ต้องเข้าใจก่อนอ่านต่อ: นี่คือการวัด WAF signature coverage เท่านั้น ไม่ใช่ full pentest ของ Juice Shop เอง (แอปตัวนี้ตั้งใจให้มีช่องโหว่อยู่แล้วโดยดีไซน์) — เป้าหมายคือวัดว่า WAF ชั้นหน้าทำหน้าที่ตามที่ออกแบบไว้แค่ไหน

§3 5 จุดที่ผ่าน WAF — และทำไมยัง "ไม่ใช่ช่องโหว่ที่ถูก exploit"

ข้อสำคัญที่ต้องพูดให้ตรง อย่าตีความเกิน

ทุก payload ในหัวข้อนี้ทดสอบแล้วว่า ไม่ถูกเอนจิน execute จริง — response ทุกตัวคือ {"status":"success","data":[]} (ค้นแล้วไม่เจอผลลัพธ์ตามปกติ ไม่มี error ไม่มี data leak ไม่มี output ของคำสั่ง) จึงเป็น WAF detection gap ไม่ใช่ confirmed exploit — endpoint นี้ของ Juice Shop ใช้ NeDB/array filter ธรรมดา ไม่มี raw SQL หรือ shell ให้ inject ได้จริงที่จุดนี้

รูปแบบที่เห็นชัด: ทั้ง WEB-03/04/05 คือเรื่องเดียวกัน — กฎจับ pattern ได้บางรูปแบบแต่ไม่ครบชุด ($(…) จับแต่ ;/backtick ไม่จับ · ${…} จับแต่ {{…}} ไม่จับ · $gt จับแต่ $ne ไม่จับ) เป็นปัญหา coverage ของ pattern ไม่ใช่ WAF ล่ม

§4 ข้อสังเกตจากการตรวจแบบ passive

Security headers

มี X-Content-Type-Options: nosniff และ X-Frame-Options: SAMEORIGIN ✅

ไม่มี Strict-Transport-Security (HSTS) และ Content-Security-Policy เลย — งานเบา แก้ที่ชั้น Caddy/nginx ได้ ไม่กระทบ logic อื่น

CORS

Access-Control-Allow-Origin: * บน API search โดยไม่มี Allow-Credentials คู่กัน — ไม่ใช่ misconfiguration อันตราย (ไม่ใช่ wildcard+credentials) เพราะเป็น public read-only data แต่ยังเปิดกว้างเกินจำเป็น

Server banner

Server: nginx ไม่มีเลขเวอร์ชัน — server_tokens off ทำงานถูกต้องแล้ว ไม่ใช่ปัญหา

§5 คำแนะนำ

  • WEB-02/03 — ปรับ CRS rule group 932xxx (Unix command injection) ให้ครอบคลุม ; และ backtick โดยไม่ต้องรอ $() · ต้องทดสอบ false positive ก่อน เพราะ ;/backtick พบในข้อความปกติได้
  • WEB-04 — เพิ่ม custom rule ครอบ {{…}} ให้เข้าเกณฑ์เดียวกับ ${…} ที่จับอยู่แล้ว
  • WEB-05 — ตรวจว่ากฎปัจจุบันจับ $gt/$lt ได้แต่พลาด $ne เพราะเขียน pattern ไม่ครบ ควรรวม MongoDB/NoSQL operator ทั้งชุดในกฎเดียว
  • HSTS + CSP — เพิ่มที่ชั้น Caddy/nginx (งานเบา ไม่กระทบ logic)
อย่าตื่นตระหนกเกินจริง — อ่านตัวเลขให้ตรง

block rate 75% สำหรับ payload เชิงรุกทั้งหมด โดยที่ SQLi ตัวรุนแรงบล็อกครบ 100% · XSS ครบ 100% · SSRF ครบ 100% · Path Traversal ครบ 100% ถือว่า core protection ทำงานตามที่ออกแบบ ช่องโหว่ที่พบเป็น pattern coverage เฉพาะจุด ไม่ใช่ WAF ล่มหรือถูก bypass ทั้งระบบ
