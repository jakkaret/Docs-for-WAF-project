10 · CDN CLASSIFICATION — คำถามจากอาจารย์ที่ปรึกษา

"ก็แค่ WAF ธรรมดาวางไว้ตามเซิร์ฟเวอร์" — จริงไหม?

อาจารย์ที่ปรึกษาตั้งคำถามว่าระบบนี้เป็น CDN ตรงไหน — เอกสารนี้ไล่ตอบทีละองค์ประกอบด้วยหลักฐานจาก SSH เข้าเครื่องจริงและอ่าน config ที่ deploy อยู่จริง ไม่ใช่การอ้างจากดีไซน์เอกสาร

§1 นิยาม CDN ที่ใช้เป็นเกณฑ์

ตำรา/อุตสาหกรรมยอมรับร่วมกันว่า CDN ต้องมีองค์ประกอบหลัก 4 อย่าง — ระบบที่ "เป็นแค่ WAF วางไว้ตามเซิร์ฟเวอร์" คือระบบที่ไม่มีข้อ 1 และ 2 เลย: แต่ละเครื่องทำงานอิสระ ไม่มี caching ไม่มีการเชื่อมโยงกัน

#องค์ประกอบทำไมถึงจำเป็น
1Caching ที่ edgeลด load ที่ origin, ตอบเร็วขึ้นเพราะไม่ต้องยิงกลับ origin ทุกครั้ง
2หลาย PoP กระจายภูมิศาสตร์ผู้ใช้แต่ละพื้นที่เข้าถึง node ที่อยู่ใกล้ตัวเอง ลด latency ทางกายภาพ
3Routing ไปหา PoP ที่เหมาะสมถ้ามีหลาย PoP แต่ทุกคนถูกส่งไปที่เดียวเสมอ ก็ไม่ต่างจากมี PoP เดียว
4Config/Rule sync รวมศูนย์ให้ทุก PoP ทำงานเป็นระบบเดียวกัน ไม่ใช่ต่างคนต่างตั้งค่า

§2 คะแนนรวม: ผ่าน 2 ใน 4

2/4 องค์ประกอบผ่าน
1 · Caching ที่ edgeผ่าน — ทำงานจริง

ตรวจ config จริงที่ generate เข้า container บน Edge Node (docker exec cdn-edge-node cat /etc/nginx/conf.d/default.conf):

proxy_cache edge_cache;
proxy_cache_key "$host|$request_method|$uri$is_args$args";
proxy_cache_valid 200 301 302 10m;   # dynamic
proxy_cache_valid 200 301 302 1h;    # static
proxy_cache_bypass $skip_cache;      # ข้าม cache ถ้ามี auth/cookie/no-cache
add_header X-Cache-Status $upstream_cache_status always;

WAF ธรรมดาไม่มีเหตุผลต้องมี cache เลย — นี่คือสิ่งที่ WAF เดี่ยว ๆ ไม่ทำ แต่ CDN edge ทำ

4 · Rule/config sync รวมศูนย์ผ่าน — ทำงานจริง

control-api (Main Node) มี /api/sync/bundle รวม rule+blocklist เป็น .tar.gz — ทุก edge poll ทุก 5 วิ เทียบ SHA-256 แล้ว reload

Edge Node มี custom rule 990001 สร้างมาเพื่อทดสอบ pipeline นี้โดยเฉพาะ — ยืนยันว่าผ่านการทดสอบใช้งานจริงแล้ว เหมือน control plane รวมศูนย์ที่ CDN เชิงพาณิชย์ใช้

2 · หลาย PoP กระจายภูมิศาสตร์ยังไม่ผ่าน

โค้ด multi-region (edge-sg, edge-jp, edge-th, geodns) เขียนเสร็จผ่านทุก test แล้ว — แต่ทดสอบบนเครื่อง dev เท่านั้น docker ps -a --filter name=cdn- บน production ยืนยันว่ามี edge จริงแค่ 1 จุด (ไทย)

นิยาม CDN ต้องมี "หลาย" PoP — เปรียบเหมือนมีพิมพ์เขียวสร้างสาขา 3 แห่งแต่เปิดขายจริงแค่สาขาเดียว ยังเรียก "เครือข่ายสาขา" ไม่ได้

3 · Geo-routing ไปหา PoP ใกล้สุดยังไม่ผ่าน

dig +short dvwa.waf-it-kku.online → 45.154.26.91 เสมอ — DNS เป็น A record ตายตัว ไม่ผ่าน GeoDNS ที่เขียนไว้ใน geodns/server.py เลย

ต่อให้เปิด GeoDNS ตอนนี้ก็ยังพิสูจน์ "ไปหา edge ใกล้สุด" ไม่ได้ เพราะมี edge จริงแค่จุดเดียว — ไม่มี "ใกล้สุด" ให้เลือกระหว่างตัวเลือกที่ไม่มีอยู่จริง

§3 Simulation: routing ตอนนี้ vs เป้าหมาย

ลองเลือกว่าผู้ใช้จำลองอยู่ภูมิภาคไหน แล้วสลับดูว่า request ของเขาถูกส่งไปที่ไหน — ระหว่างสถานะจริงตอนนี้ กับเป้าหมายเมื่อ deploy edge เพิ่ม

Simulated Routing — ไม่ใช่ค่าวัดจริง ใช้ประกอบคำอธิบายเท่านั้น

Edge: ไทยdeploy จริง
Edge: ญี่ปุ่นโค้ดพร้อม — ยังไม่ deploy

§4 ข้อบกพร่องเพิ่มเติมที่เจอระหว่างตรวจเส้นทางจริง

ระหว่างไล่ trace request จริงข้าม Edge → Main พบ 2 จุดที่ควรรู้และแก้ก่อน defend (นอกเหนือจากประเด็น CDN)

Rate-limit แยกเป็น 2 ระบบไม่เชื่อมกัน

Edge Node ใช้ limit_req แบบ static hardcode (50 req/s) ไม่เชื่อมกับ dashboard เลย ส่วน Main Node ใช้ Redis sliding-window ที่ตั้งค่าผ่าน dashboard ได้จริง — กฎที่แอดมินตั้งมีผลแค่ครึ่งทาง ไม่ครอบคลุมชั้น Edge

Traffic วิ่งแบบ plaintext HTTP ข้าม Edge→Main

Edge Node terminate TLS แล้วส่งต่อเป็น HTTP ธรรมดาข้ามอินเทอร์เน็ตสาธารณะไปหา Main Node (server 178.104.53.123:8080;) — cookie/token/payload เดินทางแบบไม่เข้ารหัสช่วงนี้ เสี่ยงต่อ MITM

§5 แนวทางทำให้เป็น CDN สมบูรณ์

  1. Deploy edge จริงอย่างน้อย 1 จุดเพิ่ม

    ภูมิภาคอื่น (เช่น VPS ถูก ๆ ที่สิงคโปร์หรือญี่ปุ่น) — เปลี่ยนสถานะจาก "PoP เดียว" เป็น "หลาย PoP" ทันที ทำให้ข้อ 2-3 ผ่านเกณฑ์

  2. เปิด GeoDNS ให้ทำงานจริง

    เมื่อมี edge 2+ จุดแล้ว โค้ดพร้อมอยู่แล้วใน geodns/server.py

  3. แก้ rate-limit ให้เป็นระบบเดียว

    ให้ Edge Node เรียก auth_request ไปที่ centralized limiter เหมือน Main Node แทน limit_req แบบ static

  4. เข้ารหัสช่วง Edge→Main

    เปลี่ยน upstream เป็น HTTPS (https://178.104.53.123:8443) พร้อม proxy_ssl_verify on

  5. ผูก dashboard เข้ากับ node จริงที่ deploy เพิ่ม

    ปัจจุบัน cdn.py ยังอ้างอิงโมเดล 2-node (TH+MAIN) ไม่ตรงกับ SG/JP/TH ที่ตั้งใจไว้

§6 สรุปสั้นสำหรับใช้ตอบอาจารย์

คำตอบตรง ๆ

"ระบบมี caching จริงที่ edge และมีการ sync กฎรวมศูนย์ข้าม node จริง — สองอย่างนี้คือกลไกหลักของ CDN ที่ WAF ธรรมดาไม่มี และพิสูจน์ได้จริงด้วย X-Cache-Status header กับการดู rule sync สด ๆ ส่วนที่ยังไม่สมบูรณ์คือยัง deploy edge ได้แค่จุดเดียว ทำให้เรื่อง geo-routing ยังพิสูจน์ไม่ได้ — เป็น future work ที่มีโค้ดพร้อมและทดสอบผ่านแล้วบน dev รอแค่ deploy จริงเพิ่ม"

อาจารย์มองจากภาพที่เห็นจริง (1 edge, DNS ชี้จุดเดียว) จึงมองว่า "เหมือน WAF วางเฉย ๆ" ซึ่งถูกต้องในมุมของสิ่งที่สังเกตเห็นได้จากภายนอก แต่ไม่ครบภาพทั้งหมดของสิ่งที่ implement ไว้ข้างใน
