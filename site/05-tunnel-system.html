05 · TUNNEL SYSTEM

4 กลไก tunnel วางซ้อนกัน — ไม่ใช่แค่เส้นทางเดียว

Web Origin อยู่หลัง VPN มหาวิทยาลัยขอนแก่น ไม่มี public IP — ต้องมีกลไกให้ origin เชื่อมต่อออกไปหา Main Node เอง (outbound) แบบเดียวกับ Cloudflare Tunnel/ngrok

อัปเดตล่าสุด: 27 ส.ค. 2026 — SSH เข้าเครื่องจริง

§1 Production: FRP Tunnel

Main Node

รัน frps (systemd frps.service) ฟัง 7000 (control), 7500 (admin API), 8085 (vhost HTTP)

Web Origin

รัน FRP client (rename /usr/local/bin/waf-agent) เชื่อม outbound ไป main.waf-it-kku.online:7000 ด้วย static token

Proxy สองเส้นทาง: dvwa.waf-it-kku.online → 127.0.0.1:8080 และ juice.waf-it-kku.online → 127.0.0.1:3000 — Dashboard (/api/tunnels/status) ดึงสถานะจาก FRP admin API cache 4 วินาที

ผู้ใช้ทั่วไป (Internet)
    │  HTTPS request → dvwa.waf-it-kku.online
    ▼
Caddy (SSL termination, Main Node)
    ▼
waf-nginx + ModSecurity CRS  ← ตรวจ/กรอง payload อันตราย
    │  (ถ้า pass การตรวจสอบ)
    ▼
frps  (vhost routing ตาม Host header, port 8085)
    │
    ▼  ── control channel (TCP, outbound จาก origin, port 7000) ──
waf-agent (FRP client บน Web Origin)
    ▼
nginx reverse proxy บน origin (waf-origin-proxy)
    ▼
Container ปลายทาง (dvwa หรือ juice-shop) ตอบกลับ
request วิ่งเข้าจากอินเทอร์เน็ตที่ Main Node ก่อนเสมอ แล้วค่อยถูกส่งผ่าน tunnel เข้าไปหา origin — origin ไม่เคยเปิด inbound port เลย

§2 เส้นทางที่ข้าม WAF

Cloudflare Tunnel — dvwa-tunnel.service

run_tunnel.sh รัน cloudflared แบบ Quick Tunnel (สุ่มโดเมน *.trycloudflare.com ทุก restart) — URL ที่พบ active จริง: clocks-exclusion-tee-gratis.trycloudflare.com — ไม่ผ่าน WAF ของ Main Node เลย เหมาะ demo/debug เท่านั้น

Public Lab Hub — waf-tunnel.service

/opt/waf-lab/tunnel_manager.py เปิด Cloudflare Quick Tunnel แยกให้ทุกแอปพร้อมกัน (hub/juice/dvwa/vampi/bwapp) generate หน้า dashboard HTML — เส้นทางนี้ก็ไม่ผ่าน WAF เช่นกัน

§3 Custom Zero-Trust Tunnel Protocol — เขียนเสร็จ ยังไม่ deploy

พบ scripts/waf_tunnel_server.py (Main Node) และ scripts/waf_tunnel_agent.py (client) — โปรโตคอลเขียนเองไม่พึ่ง FRP เลย จุดต่างสำคัญจาก FRP:

  • Per-tenant token ตรวจผ่าน POST /api/auth/tunnel/verify แทน static token เดียวที่ทุกคนใช้ร่วมกัน
  • Backend สืบค้น origin จาก DynamoDB แล้วตอบ remote_bind_port เฉพาะ origin นั้น — แต่ละลูกค้าได้ port แยกกัน
  • Binary framing เอง (header 21 byte) รองรับ AUTH / AUTH_RESP / CONNECT / DATA / CLOSE
สถานะจริง

ไม่มี systemd unit ไม่มี process รันค้างบน port 8050 — พบเพียงไฟล์ test_tunnel_flow.py ที่ spawn server+agent ชั่วคราวเพื่อ integration test แล้ว teardown ทิ้ง

§4 Scenario: Origin รีสตาร์ทแล้วเชื่อมกลับ

  1. Web Origin รีบูต

    เช่นตอน dvwa-ctl restart หรือเครื่องปิดโดยไม่ตั้งใจ

  2. waf-agent.service พยายามเชื่อมใหม่

    systemd Restart=always เชื่อม outbound ไปหา frps อัตโนมัติ

  3. Auth สำเร็จ → register proxy ใหม่

    ทั้งสอง proxy กลับมาที่ฝั่ง server

  4. ระหว่างยังไม่ reconnect

    request ที่เข้ามาเจอ error จริงในlog: no route found: dvwa.waf-it-kku.online /

§5 แนวทางพัฒนาต่อ

  • ย้ายไปใช้ custom zero-trust tunnel เป็นระบบหลัก — แก้จุดอ่อนสำคัญของ FRP คือ token เดียวใช้ร่วมกันทั้งระบบ
  • ปิดเส้นทางที่ข้าม WAF หรือจำกัดเฉพาะ dev/debug environment
  • เพิ่ม HA ให้ FRP server — ปัจจุบันเป็น single point of failure
  • Auto-reconnect/health monitoring ที่ดีขึ้น — พบ error no route found เป็นระยะ ควรมี Telegram alerting
  • หมุนเวียน token/credential ที่เป็น static values อยู่ใน .toml
