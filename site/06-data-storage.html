06 · DATA STORAGE

5 กลไกเก็บข้อมูลคู่ขนาน — เลือกตามลักษณะข้อมูล ไม่ยัดที่เดียว

Polyglot persistence: เลือกเครื่องมือให้เหมาะกับงาน แทนที่จะยัดทุกอย่างลงฐานข้อมูลเดียว

ระบบเก็บอะไรเหตุผล
ClickHouseAccess log + security audit log ปริมาณมากColumn-oriented, aggregate/filter บนข้อมูลนับล้านแถวได้เร็ว
DynamoDB (AWS จริง)alert, rule, user, origin, domain, SSL cert, pending ruleNoSQL latency ต่ำ ทนทาน ไม่ต้อง migrate schema เอง
RedisSliding-window counter สำหรับ rate limitIn-memory, atomic ผ่าน Lua, sub-millisecond
SQLiterate_limits.db, ip_rules.dbconfig เครื่องเดียวใช้ ไม่ต้อง sync ข้ามเครื่อง
JSON filesystem_settings.jsonข้อมูลเล็ก เปลี่ยนไม่บ่อย

DynamoDBService ต่อ region ap-southeast-1 — ยืนยันว่า ไม่ได้ตั้งค่า DYNAMODB_ENDPOINT_URL จึงต่อ AWS DynamoDB จริงบนคลาวด์ ไม่ใช่ local emulator

§1 ความสามารถ

access_logs สะสมจริงทำงานจริง

113,336 แถว ณ ตอนตรวจสอบ ยืนยันว่าระบบถูกใช้งาน/ทดสอบต่อเนื่องจริง — ไม่ใช่แค่โครงเปล่า

Rate limiting sliding windowทำงานจริง

Redis Sorted Set (ZADD/ZREMRANGEBYSCORE/ZCARD) atomic ด้วย Lua — fail-open ถ้า Redis ล่ม

waf_pending_rules composite keyทำงานจริง

(rule_id + created_at) พร้อม GSI status-index — สะท้อน workflow "เสนอกฎ → รออนุมัติ" จริง

waf_users GSI 2 ตัวทำงานจริง

EmailIndex + ProviderIndex (auth_provider+provider_id) รองรับ multi-provider login

ClickHouse query ต่อ string ตรง ๆช่องโหว่

get_logs()/get_filter_options() escape ' แบบพื้นฐานเท่านั้น ไม่ใช่ parameterized query จริง

DynamoDB ใช้ scan() เป็นหลักหนี้เทคนิค

get_logs()/get_all_alerts() อ่านทั้งตารางแล้วกรองที่ backend — ไม่ scale ดีเมื่อข้อมูลโต

In-memory cache ไม่ sync ข้าม instanceหนี้เทคนิค

_alerts_cache TTL 5 วิ เป็น cache ระดับ process เดียว

ไม่มี TTL/retention policyหนี้เทคนิค

access_logs โตไปเรื่อย ๆ ไม่มีลบอัตโนมัติ

§2 การไหลของข้อมูล

เส้นทางที่ 1 — Request ที่ถูก WAF บล็อก:
Client ยิง payload อันตราย
  → ModSecurity CRS ตรวจจับ (WAF container)
  → บันทึก /var/log/modsecurity/audit.json
  → log forwarder อ่านไฟล์ → ส่งเข้า backend
  → ClickHouseService.save_log("access_logs", data) status_code=403
  → เหตุการณ์ร้ายแรง → DynamoDBService.save_alert() → waf_alerts
  → Dashboard เรียก GET /logs → แสดงตาราง/กราฟ

เส้นทางที่ 2 — Rate limit แบบ real-time:
Request เข้า endpoint
  → RedisRateLimiter.is_allowed(ip, limit, window)
  → Lua script เช็ค sliding window ภายใน 1 round-trip (atomic)
  → เกิน limit → 429 ทันที ไม่ปล่อยผ่านไป origin
  → กติกา limit/window ดึงจาก SQLite (rate_rules)

§3 แนวทางพัฒนาต่อ

  • เปลี่ยน ClickHouse query filter ทั้งหมดเป็น parameterized query (clickhouse_connect รองรับอยู่แล้ว)
  • เพิ่ม TTL policy ให้ตาราง ClickHouse เช่น TTL timestamp + INTERVAL 90 DAY
  • ย้าย in-memory alert cache ไปใช้ Redis เพื่อ scale หลาย instance ได้
  • ทำ DynamoDB Local แยกสำหรับ dev/test ตั้ง DYNAMODB_ENDPOINT_URL จริงจัง
