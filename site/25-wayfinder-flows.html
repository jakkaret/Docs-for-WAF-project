§2 เกิดอะไรขึ้นเมื่อแต่ละชั้นล้ม — fail-open หรือ fail-closed

ตารางนี้สำคัญกว่าที่คิด: ระบบที่ "fail-closed" (ปฏิเสธเมื่อไม่แน่ใจ) ปลอดภัยกว่าระบบที่ "fail-open" (ปล่อยผ่านเมื่อไม่แน่ใจ) เสมอในบริบทความปลอดภัย — แต่ที่แย่ที่สุดคือ "fail-closed แบบแขวน" ซึ่งไม่ปฏิเสธและไม่ปล่อยผ่าน แค่ค้างจนกว่า client จะ timeout เอง

ชั้นที่ล้มพฤติกรรมที่สังเกตได้ประเภท
Dashboard /api/limiter/check ไม่ตอบnginx auth_request ค้าง → request ค้างจนหมด timeout (วัดได้ 40 วินาที)fail-closed แบบแขวน — แย่ที่สุด
Redis ล่มRedisRateLimiter จับ exception → ปล่อยผ่านfail-open
ClickHouse ล่มข้ามการเขียน, query คืนค่าว่างfail-open — ข้อมูลหายเงียบๆ
DynamoDB ล่มsave_log จับ exception พิมพ์ logfail-open
tunnel agent หลุด (CloudWAF)502 "No tunnel agent" / ไม่ตอบใน 10 วิ → 504fail-closed ชัดเจน (ดี)
verifier ต่อไม่ได้tunnel server ปฏิเสธ agentfail-closed — มีคอมเมนต์ระบุเจตนา
frps httpPlugin ไม่ตอบfrps ปฏิเสธ proxyfail-closed
edge → main:8000 ไม่ได้retry exponential backoff, buffer 5000, ล้นแล้วทิ้งตัวเก่าfail-open + ข้อมูลหาย
origin ล่มแต่ edge มี cacheตอบ X-Cache-Status: STALEfail-open โดยตั้งใจ
gatekeeper เจอ op ที่ไม่รู้จักreject พร้อมเหตุผลfail-closed — ตั้งใจ
