07 · WEB ORIGIN TESTBED

เครื่องเป้าหมาย 4-in-1 สำหรับพิสูจน์ว่า WAF ทำงานจริง

ต่างจาก Edge/Main Node ที่รัน WAF engine เครื่องนี้มีหน้าที่เดียวคือโฮสต์เว็บแอปที่มีช่องโหว่ตั้งใจ ไว้เป็นเป้าหมายทดสอบ

เครื่อง: 10.198.200.75 (private, หลัง KKU VPN)สเปก: Ubuntu 24.04.4 · 16 vCPU · 15 GiB RAM

§1 เว็บแอปช่องโหว่ทั้ง 4

แอปเทคโนโลยีบทบาท
DVWAvulnerables/web-dvwa + MariaDBช่องโหว่คลาสสิกครบ (SQLi, XSS, CSRF, Command Injection)
OWASP Juice ShopNode.jsอีคอมเมิร์ซจำลอง สอน OWASP Top 10 ครอบคลุมช่องโหว่สมัยใหม่กว่า DVWA
vAmPIFlask REST APIสำคัญที่สุด — ทดสอบ BOLA/IDOR, mass assignment, excessive data exposure
bWAPPPHPช่องโหว่ครอบคลุมกว้างสุด (100+) รวม XXE, SSRF, LDAP Injection

§2 ความสามารถ

Reverse proxy แยกตาม subdomainทำงานจริง

nginx waf-lab.conf แยก virtual host juice.* / dvwa.* / vampi.* / bwapp.* พร้อม TLS และ header มาตรฐาน

Real-IP restoration ถูกต้องทำงานจริง

ครอบคลุม Cloudflare IP range ทั้งหมด — log เห็น IP ผู้ใช้จริงแทน IP ของ proxy คั่นกลาง

Container ทั้ง 4 ตัวรันจริงและ healthyทำงานจริง

ตรวจผ่าน docker ps — compose project waf-lab ที่ /opt/waf-lab

Public exposure ผ่าน Cloudflare Quick Tunnelทำงานจริง

active_urls.json มี URL active สำหรับทั้ง 5 endpoint

Port แอปเปิดตรงจาก hostช่องโหว่

3000/8080/5000/8081 — เข้าถึง VPN วงเดียวกันได้ = เข้าถึงแอปช่องโหว่ได้โดยไม่ผ่าน WAF เลย

DVWA security level = lowConfig เสี่ยง

default_phpids_level = 'disabled' — เหมาะ demo แต่ยังไม่ทดสอบระดับ high/impossible เพื่อวัด false-positive

Deployment 2 ชุดซ้อนกันหนี้เทคนิค

/opt/dvwa-origin เก่า vs /opt/waf-lab ที่รันจริง — container name ซ้อนทับกันบางส่วน เสี่ยงชนตอน reboot

Quick Tunnel URL สุ่มใหม่ทุก restartหนี้เทคนิค

ไม่ใช่ named tunnel ที่ผูกโดเมนถาวร — ต้องอัปเดต URL มือทุกครั้ง

§3 การไหลของข้อมูล

[ผู้ใช้/นักพัฒนาที่ทดสอบ WAF]
        │
        ▼
[Edge Node / Main Node — WAF + CDN]  (ตรวจสอบ/บล็อก payload อันตรายก่อน)
        │  (traffic ที่ผ่าน WAF แล้ว หรือทดสอบตรง)
        ▼
[Cloudflare Quick Tunnel]  ← outbound connection ที่ Web Origin เปิดค้างไว้
        │
        ▼
[waf-origin-proxy (nginx, :80/:443)]  ← Web Origin (10.198.200.75)
        │  แยกเส้นทางตาม subdomain
        ├──► waf-juice-shop:3000   (Node.js app)
        ├──► waf-dvwa-app:80 ──► waf-dvwa-db:3306 (MariaDB)
        ├──► waf-vampi:5000       (Flask API)
        └──► waf-bwapp:80         (PHP app)

§4 Scenario: ทดสอบว่า WAF บล็อก SQLi ได้จริงหรือไม่

  1. เปิด URL ทดสอบ

    ผ่าน Cloudflare Tunnel หรือโดเมนที่ตั้งไว้ในระบบ WAF ที่ชี้มาที่ origin นี้

  2. ถ้า route ผ่าน Edge/Main Node จริง

    ModSecurity CRS ตรวจ id=1' OR '1'='1 — anomaly score เกิน threshold → บล็อกทันที ไม่ถึง origin

  3. ถ้าทดสอบตรงเข้า origin (baseline)

    ผ่าน VPN โดยไม่ผ่าน WAF — payload เดียวกันสำเร็จ (DVWA security level = low ไม่มีป้องกันในตัวแอปเอง)

  4. เปรียบเทียบสองกรณี

    คือวิธีหลักที่ใช้พิสูจน์ประสิทธิภาพจริงของ WAF

เสริม ทดสอบ BOLA บน vAmPI

เรียก GET /users/2/records ขณะ login เป็น user ID 1 — ถ้าระบบตรวจ authorization ไม่ครอบคลุมระดับ object vAmPI จะคืนข้อมูล user อื่นกลับมา แสดงชัดว่า WAF แบบ signature-based ป้องกัน BOLA ไม่ได้ด้วยตัวเอง เพราะเป็นปัญหา business logic ไม่ใช่ payload pattern — เหตุผลที่ระบบมี bola_guard.py แยกต่างหาก
