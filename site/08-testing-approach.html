08 · แนวทางการทดสอบระบบ

ทดสอบ WAF ให้ตอบ 4 คำถาม ไม่ใช่แค่ "ยิงแล้วดูว่าบล็อกไหม"

Detection, false positive, coverage gap, resilience — พร้อมคำสั่งจริงที่ใช้ทดสอบไปแล้วและผลจริงที่ได้ (27 ส.ค. 2026) อ้างอิงจากสถาปัตยกรรมในเอกสาร 00-07

§1 เป้าหมายของการทดสอบ — 4 คำถามหลัก

1 · Detection

WAF ตรวจจับการโจมตีที่รู้จักได้จริงหรือไม่ (true positive)

2 · False Positive

WAF บล็อก traffic ปกติผิดหรือไม่ — ถ้าสูงเกินไป ใช้งานจริงไม่ได้

3 · Coverage Gap

มีเส้นทางไหนเข้าถึง origin ได้โดยไม่ผ่านการตรวจสอบเลยหรือไม่ (เช่นทางลัดที่เจอแล้วในรายงาน 05/09)

4 · Resilience

ระบบรับมือ traffic ปริมาณมาก (rate limit) หรือ payload obfuscate ได้แค่ไหน

§2 ขอบเขตและข้อควรระวังก่อนเริ่ม

  • ทดสอบผ่านเส้นทางที่ WAF ป้องกันจริงเท่านั้น (dvwa.waf-it-kku.online, juice.waf-it-kku.online) — ใช้เส้นทาง Cloudflare Quick Tunnel bypass เฉพาะตอนต้องการเปรียบเทียบเท่านั้น ไม่ใช่เส้นทางทดสอบหลัก
  • ไม่ทดสอบแบบทำลายข้อมูลจริง — payload ต้องเป็นแค่ probe ไม่ใช่ยิง DROP TABLE ใส่ DVWA จริงจนข้อมูล demo พัง
  • จำกัดความถี่ของการทดสอบเอง — ทุก request (แม้โดนบล็อก) ถูกบันทึกลง ClickHouse จริง ยิงเยอะเกินจะทำให้ analytics มี noise ปนกับข้อมูลโจมตีจริง
  • แจ้งเตือนจะเข้า Telegram ของแอดมินจริง — payload severity สูงจำนวนมากอาจส่งข้อความเข้าโทรศัพท์เป็นชุดโดยไม่ตั้งใจ

§3 หมวดการทดสอบ

3.1 · Core Detectionผ่านครบ

Baseline พื้นฐานที่สุด — SQLi, XSS reflected, path traversal, command injection ยิงด้วย curl ทั้ง 4 ตัวได้ 403 ครบ ยืนยัน OWASP CRS มาตรฐานทำงานถูกต้องผ่าน production จริง

ขั้นต่อไป: sqlmap -u URL --batch --level=3 --risk=1 เพื่อทดสอบ WAF-bypass technique อัตโนมัติ (encoding variation, comment injection)

3.2 · Custom Rule Verificationผ่านครบ

พิสูจน์ pipeline สร้าง/sync กฎเอง ไม่ใช่แค่ WAF เก่งอยู่แล้ว — testattack และ admin1 keyword ได้ 403 ทั้งคู่ ยืนยันว่ากฎที่สร้างผ่าน dashboard sync ไปถึง WAF จริง

ขั้นต่อไป: สร้างกฎใหม่ผ่าน UI จริง จับเวลาว่า sync ถึง edge ภายใน ~5-10 วิ ตามที่ออกแบบไว้หรือไม่

3.3 · False Positive / Baselineพบบั๊ก

ยิง / ได้ 404 ไม่ใช่ 403 หรือ 200 ตามคาด — ไม่ใช่ WAF บล็อก (ไม่มี header deny จาก ModSecurity) แต่เป็นบั๊ก routing ที่ origin ไม่มี path นี้แมปไว้ ไม่ใช่ปัญหา security แต่ผู้ใช้จริงเข้าครั้งแรกจะเจอหน้า 404 ทันที

3.4 · Rate Limitingต้องปรับวิธี

ทดสอบด้วย loop curl sequential 25 ครั้ง — ไม่ทริกเกอร์ 429 เลย เพราะ sequential มี latency คั่นตามธรรมชาติ ทำให้ throughput ต่ำกว่า 50 req/s มาก ต้องยิงพร้อมกันจริง (concurrent) ด้วย hey -n 300 -c 60 -q 0 ถึงจะเห็นผล

3.5 · WAF Fingerprintingพบจุดควรปรับปรุง

response header ทุก request มี X-Edge-Region: TH และ X-Cache-Status: MISS ติดมาด้วย — เซ็ตแบบ static ไว้ล่วงหน้าใน nginx config ทั้งที่ CDN multi-region ยังไม่ deploy จริง เสี่ยง information leakage และสร้างความเข้าใจผิด ควรลบด้วย more_clear_headers

3.6 · API Security / BOLA (vAmPI)มี pre-requisite ต้องแก้ก่อน

vAmPI ไม่ได้ผูกกับ FRP tunnel ที่ผ่าน WAF (มีแค่ dvwa/juice ที่ลงทะเบียนกับ frps) — เข้าถึงได้ทางเดียวคือผ่าน Cloudflare Quick Tunnel ที่ข้าม WAF ไปเลย ยังทดสอบ BOLA ผ่าน WAF จริงไม่ได้เลยในสภาพปัจจุบัน ต้องเพิ่ม vampi.waf-it-kku.online เข้า FRP config ก่อน

3.7 · WAF Bypass Path Comparisonยังไม่ได้ทำ

ยิง payload เดียวกันสองเส้นทาง (ผ่าน WAF vs ผ่าน Cloudflare Quick Tunnel) เพื่อวัดขนาดความเสี่ยงที่ระบุไว้แล้วในรายงาน 05/07 ให้เห็นเป็นรูปธรรม — คาดว่าเส้นทางแรก 403, เส้นทางที่สอง 200 พร้อม SQLi สำเร็จจริง (DVWA security level = low)

3.8 · Evasion / Obfuscationยังไม่ได้ทำ

ทดสอบ double URL encoding, SQL comment splitting, null-byte injection — ตรงกับ evasion technique ที่ payload_normalizer.py เขียนไว้ว่ารองรับ ถ้าหลุดผ่านไปได้ (ไม่ใช่ 403) แปลว่า logic การ decode ยังไม่ครอบคลุมจริง

§4 ลองรันชุดทดสอบเอง (จำลองจากผลจริง)

คลิกชุดทดสอบด้านล่างเพื่อดูคำสั่งที่ใช้และผลจริงที่บันทึกไว้ (27 ส.ค. 2026) — ไม่ใช่การยิง request จริงจากหน้านี้ แต่เป็นการเล่นซ้ำผลที่วัดได้จริงแล้ว

คลิกปุ่มด้านบนเพื่อดูผลจริง

§5 ลำดับการทดสอบที่แนะนำ

เริ่มจากพิสูจน์พื้นฐานว่าระบบทำงานก่อนไปทดสอบขีดจำกัด แล้วค่อยขยายไปหาจุดที่ซับซ้อนกว่า — สลับลำดับแล้วจะแยกไม่ออกว่าปัญหาคือขั้นพื้นฐานพังหรือเป็นจุดซับซ้อนเฉพาะทาง

  1. Core Detection + False Positive baseline

    ทำคู่กันเสมอ อย่าทำแค่ฝั่งใดฝั่งหนึ่ง

  2. Custom Rule Verification

  3. แก้ pre-requisite ของ BOLA testing ก่อน

    ผูก vAmPI เข้า FRP tunnel แล้วค่อยทดสอบ BOLA

  4. WAF Bypass Comparison

    ยืนยัน severity ของช่องโหว่ที่ระบุไว้แล้วว่าสำคัญ — ควรทำเร็ว ๆ

  5. Evasion Testing

  6. Rate Limiting

    ทำท้าย ๆ เพราะกระทบปริมาณ log/analytics มากที่สุด

  7. WAF Fingerprinting

    ทำเมื่อไหร่ก็ได้ ไม่ขึ้นกับขั้นตอนอื่น

§6 ข้อควรระวังสรุปรวม

  • ทดสอบผ่านโดเมนที่ WAF ป้องกันจริงเป็นหลัก ใช้เส้นทาง bypass เฉพาะตอนต้องเปรียบเทียบเท่านั้น
  • อย่าใช้ payload ระดับทำลายข้อมูล แม้เป็นระบบทดสอบของตัวเองก็ตาม เพราะแอปช่องโหว่ใช้ demo ข้อมูลร่วมกันหลายจุด พังแล้วต้อง reset ใหม่
  • ทดสอบ rate limit แยกเวลากับหมวดอื่น เพราะปริมาณ request สูงจะกลบข้อมูลการทดสอบหมวดอื่นใน log
  • คำนวณผลกระทบต่อ Telegram alert ก่อนยิง payload severity สูงจำนวนมากรวดเดียว
