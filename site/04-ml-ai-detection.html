04 · ML + AI DETECTION

โมเดล ML จริง ไม่ใช่ mock — บวก AI Copilot ที่มี fallback ทุกจุด

สองระบบแยกบทบาท: ML Anomaly Detection (Random Forest + Isolation Forest) ให้คะแนนความเสี่ยงและเสนอกฎใหม่ กับ Gemini AI Layer สำหรับอธิบาย/แชท/สรุปรายงาน — ไม่ทับซ้อนกัน

ทำงานที่: ml_api :5000 (standalone) + Dashboard Backend :8070

0Accuracy
0Benign recall (FP แค่ 77/7,454)
0Attack recall (พลาด ~38%)
0Attack precision

เทรนจาก 60,106 samples (train 45,079 / test 15,027) — Random Forest (n_estimators=200, max_depth=20) + Isolation Forest (n_estimators=150) · ยืนยันจาก eval_results.json จริง

Feature ที่มีน้ำหนักมากสุด: keyword_matches (31.3%), special_char_ratio (21.1%), special_char_count (18.8%) — โมเดลพึ่งพา keyword/regex signal เป็นหลัก

§1 ความสามารถ

13-feature engineeringทำงานจริง

decode URL 2 ชั้นก่อนสกัด — ครอบคลุม SQLi/XSS/Path Traversal/RCE/SSRF/SSTI/NoSQL/Log4j-JNDI

predict-and-suggestทำงานจริง

เจอ anomaly → auto-generate SecRule ผ่าน auto_rule_generator.py → บันทึกเป็น pending rule ใน DynamoDB

Human-in-the-loop โดยตั้งใจทำงานจริง

ไม่มี auto-block — admin ต้อง approve/reject ทุกกฎที่ ML เสนอ ตรงตาม proposal ที่ระบุว่า auto-block เสี่ยง false positive สูง

AI Copilot chatทำงานจริง

ดึง telemetry สดจาก ClickHouse ฝัง system prompt ทุกครั้ง, scope ตาม origin ที่ user ดูแลจริง, failover 4 โมเดล + fallback แบบไม่ใช้ AI

Explainability Engine (แยกจาก ML/AI)ทำงานจริง

regex signature-matching ล้วน ๆ (ไม่ใช่ SHAP/LIME) แปล rule ID → คำอธิบายไทย+remediation ไม่มีค่าใช้จ่าย API

explain_attack() cacheทำงานจริง

TTL 5 นาทีต่อ signature (method+url+rule_id+attack_type) ลดเรียกซ้ำ, มี fallback ข้อความสำเร็จรูปถ้า Gemini ล่ม

Attack recall แค่ 62%ข้อจำกัด

พลาดตรวจจับจริงเกือบ 4 ใน 10 — แต่ ModSecurity CRS ยังเป็นด่านหลัก ML เป็นชั้นเสริมเท่านั้น

Entropy feature เป็น dead codeDead code

calculate_shannon_entropy() มีอยู่จริงแต่ไม่ถูกใส่เข้า FEATURE_COLUMNS ที่โมเดลเทรนจริง

Daily-cron cost control ไม่ implementช่องว่างจาก proposal

proposal ต้องการเรียก Gemini วันละครั้งผ่าน cron แต่โค้ดจริงเป็น on-demand endpoint ล้วน — ค่าใช้จ่าย API อาจสูงกว่าแผนถ้า traffic โจมตีสูง

ไม่มี closed-loop retrainingช่องว่าง

ผล approve/reject ของแอดมินไม่ถูกป้อนกลับไปเทรนโมเดลใหม่ (ยืนยันด้วย grep ทั้ง repo)

§2 หลักการทำงาน — 3 เส้นทาง

เส้นทาง 1 — Manual prediction

แอดมิน/ระบบส่ง (url,method,body) → /predict-and-suggest → 13 features → RF+IF ให้คะแนน → เจอ anomaly → generate SecRule → pending rule → approve → sync เข้า WAF จริง

เส้นทาง 2 — Blocked → คำอธิบายอัตโนมัติ

ModSecurity บล็อกจริง (403) → log ClickHouse → explainability_service จับคู่ rule ID ทันที (ไม่มีค่าใช้จ่าย) → อาจเรียก Gemini สรุปสั้นเพิ่มสำหรับ Telegram

เส้นทาง 3 — AI Copilot chat

แอดมินพิมพ์คำถาม → ดึง origin/domain ที่ scope ไว้ → query ClickHouse สด 24 ชม. → ฝัง telemetry เข้า prompt → ไล่โมเดล 4 ตัวถ้าโดน rate limit

§3 Scenario: SQL Injection เข้า login endpoint

GET /api/v1/auth/login?id=1' OR '1'='1' --

  1. ModSecurity CRS จับได้ทันที

    rule กลุ่ม 942xxx match pattern or\s+['\"]?1['\"]?\s*=\s*['\"]?1 → บล็อก 403 ก่อนถึง origin

  2. Log เข้า ClickHouse

    access_logs

  3. Explainability engine อธิบายทันที

    confidence 0.95 → "ตรวจพบรูปแบบ SQL Injection... แนะนำ Parameterized Queries" — ไม่เรียก Gemini

  4. Telegram alert (แยกกัน)

    gemini_service.explain_attack() อาจถูกเรียกสรุปเป็นประโยคไทยสั้น ๆ

  5. แอดมินวิเคราะห์ด้วย ML

    กด "วิเคราะห์ด้วย ML" → RF ให้ attack_probability สูง, IF ให้ anomaly_score ติดลบ → เสนอกฎใหม่เข้าคิว

  6. Approve → deploy

    คุ้มครองล่วงหน้าแม้ยังไม่เจอ payload แบบนี้จาก IP อื่นมาก่อน
