19 · MAIN SERVER ANALYSIS — 2 ก.ย. 2026

ผ่าเครื่อง Main ทีละฟีเจอร์ — มีอะไรบ้าง ทำงานยังไง และอะไรที่ไม่ตรงกับที่เคยอ้าง

สำรวจเฉพาะเครื่อง Main (178.104.53.123) ผ่าน SSH เข้าเครื่องจริง อ่าน source code จริง เรียก API จริง และยิง HTTP ทดสอบจริง — ได้ทั้งแผนที่ฟีเจอร์ทั้งหมด 15 กลุ่ม และเจอเรื่องที่เอกสารเดิมอธิบายไม่ตรงกับความจริง 4 ข้อ

ที่รันจริง 5 systemd service · 6 container · 98 API endpoint พบใหม่ 4 ข้อ — รวมถึง BOLA Guard ที่ไม่ได้อยู่ใน request path จริง

§1 Main คือเครื่องอะไรในระบบ

ต่างจาก Edge (ด่านหน้า กระจายโหลด/แคช) และ Lab (เว็บเป้าหมายให้ทดสอบ) — Main คือสมองของระบบ ถือ 4 บทบาทพร้อมกัน

Control Plane

เก็บกฎ ผู้ใช้ โดเมน และแจกจ่ายกฎออกไปให้ Edge ผ่าน control-api

Data Plane

ตรวจ traffic ด้วย ModSecurity แล้วส่งต่อเข้า tunnel ไปยัง origin

Intelligence Plane

ML ตรวจจับ + feature attribution + AI อธิบาย/สรุปด้วย Gemini

Tunnel Hub

ปลายทางที่ agent จากเครื่องหลัง NAT วิ่งเข้ามาต่อ (2 ระบบพร้อมกัน)

ทรัพยากรจริงตอนสำรวจ: RAM 3,814 MB (ใช้ 1,903 / เหลือใช้ได้ 1,911), ดิสก์ 38 GB ใช้ 49%, uptime 9 วัน

§4 ฟีเจอร์ทั้งหมด — คืออะไร ทำงานยังไง

Backend มี 98 endpoint ที่ mount จริง แบ่งเป็น 19 กลุ่ม (นับจาก /openapi.json ของเครื่องจริง) คลิกกรองดูตามประเภทได้

4.1 · WAF Engine (ModSecurity + CRS)ยืนยันสด

คืออะไร: ตัวที่บล็อกการโจมตีจริง — หัวใจของระบบ

ทำงานยังไง: nginx ที่ฝัง ModSecurity v3 โหลดกฎ OWASP CRS (32 ไฟล์) + กฎที่เราเขียนเอง ตรวจใน phase 2 (หลังอ่าน body) ถ้าเข้าเกณฑ์ตอบ 403 ทันทีโดยไม่ส่งต่อไป origin

ทดสอบจริง: ยิง SQLi เข้าทั้ง 4 โดเมน → 403 ทุกโดเมน

ต้องพูดตรงๆ: กฎ custom ที่ active ทั้ง 6 ข้อ (testattack, pwd01, admin1, seminar, testpj, /test-waf-sync-rule) เป็น ระดับ demo/ทดสอบทั้งหมด ไม่มีข้อไหนเป็น signature เชิงลึกที่เพิ่มจาก CRS — ความสามารถตรวจจับจริงมาจาก CRS ล้วนๆ

4.2 · Rule Management + Rule Sync ไป Edgeยืนยันสด

คืออะไร: ให้แอดมินเขียน/แก้/ลบกฎจากหน้าเว็บ แล้วกฎมีผลทั้ง Main และ Edge

ทำงานยังไง: สร้างกฎผ่าน POST /api/rules/ → rule_manager.py เขียนไฟล์ .conf → nginx -s reload (graceful ไม่ตัด connection ที่ค้าง) → control-api mount โฟลเดอร์เดียวกัน เปิด GET /api/sync/bundle ให้ Edge มาดึง → Edge poll ทุก 5 วินาที เทียบ SHA-256 ต่างค่อยโหลดใหม่

ค่าที่เขียนลงไฟล์กฎถูก escape ด้วย escape_secrule_string() แล้ว หลังพบช่องโหว่ SecRule injection (หน้า 17 §7)

4.3 · Blast Radius Simulatorอ่านโค้ด — 561 บรรทัด

คืออะไร: เครื่องมือ "ลองก่อนใช้จริง" — ก่อน deploy กฎใหม่ ประเมินว่ากฎนี้จะบล็อกผู้ใช้จริงไปกี่คน

ทำงานยังไง: ดึง access log ย้อนหลังจาก ClickHouse มา replay กับกฎที่กำลังจะสร้าง (ในหน่วยความจำ ไม่แตะกฎจริง) แล้วคำนวณ False Positive Rate, True Positive Rate, Risk Level (SAFE/WARNING/HIGH) และ endpoint/subnet ที่กระทบมากที่สุด

ทำไมสำคัญ: นี่คือคำตอบของปัญหา false positive ที่โปรเจกต์ตั้งใจแก้ — เป็นฟีเจอร์ที่แยกโปรเจกต์นี้ออกจาก "ModSecurity เปล่าๆ" ได้ชัดที่สุด

4.4 · Rate Limiting (ทำงาน inline บน traffic จริง)ยืนยันสด

ทำงานยังไง — จุดนี้น่าสนใจทางสถาปัตยกรรม: nginx ใช้ auth_request เรียกกลับเข้ามาที่ backend /api/limiter/check ก่อน ส่ง request ต่อไป origin ทุกครั้ง backend เช็คกับ Redis แล้วตอบว่าให้ผ่านไหม เกินโควตาจะส่ง Retry-After กลับให้ nginx ตอบ 429

  • Redis เก็บเป็น sorted set (ZSET) ทำ sliding window
  • ใช้ Lua script รันฝั่ง Redis ให้ check-and-increment เป็น atomic (กัน race condition)
  • whitelist ไม่นับ static asset เพื่อไม่ให้หน้าเว็บพัง

4.6 · Feature Attribution (งานหลักของ thesis)ยืนยันสด

คืออะไร: บอกได้ว่าโมเดลคิดว่าอันนี้เป็นการโจมตี เพราะ feature ตัวไหน มีน้ำหนักเท่าไร ไม่ใช่แค่คะแนนรวม

ทำงานยังไง: ml/attribution.py เดิน tree path ของ Random Forest เอง แต่ละ node ที่เดินผ่านคำนวณส่วนต่างของ P(class=1) แล้วยกความดีความชอบให้ feature ที่ใช้ split node นั้น รวมทุกต้นในป่าแล้วเฉลี่ย

ทำไมไม่ใช้ SHAP: RAM บน Main จำกัด (3.8 GB) และ shap ลาก numba/llvmlite มาด้วยซึ่งหนักเกินไป — implement เองด้วย numpy/pandas ล้วน ความถูกต้องพิสูจน์ทางคณิตศาสตร์: bias + Σ contribution = predict_proba เป๊ะ

4.7 · Real-time Log Analyzer + Auto Rule Suggestionยืนยันสด

ทำงานยังไง: tail ไฟล์ log แบบ async หลาย channel → ยิงเข้า /predict → ถ้า probability สูงเรียก /generate-rule ต่อ → กฎไปอยู่ในตาราง waf_pending_rules สถานะ รออนุมัติ ไม่ deploy เอง

4.8–4.9 · Explainability + AI Copilot (Gemini)อ่านโค้ด

Explainability: แปล rule ID ดิบ (เช่น 942100) เป็นคำอธิบายภาษาไทย พร้อมชี้ token ที่เป็นตัวปัญหา ทำงานภายในเครื่อง ไม่เสียค่า API

4.10 · Multi-tenant: Origins / Domains / Usersอ่านโค้ด

โครงสร้าง 3 ชั้น: User (บัญชี + role) → Origin (server ปลายทาง ip+port) → Domain (ชื่อโดเมนที่ชี้มาหา origin, 1 origin มีได้หลายโดเมน)

Quota 5 origin ต่อบัญชี · 10 โดเมนต่อ origin · การลบเป็น soft-delete (เปลี่ยน status เป็น archived กู้คืนได้) · แยก tenant ด้วย verify_origin_ownership() ทุกครั้ง + cache 3 วินาที

§5 สิ่งที่พบว่าไม่ตรงกับที่เอกสารเคยอ้าง

หัวข้อนี้แยก คำกล่าวอ้าง ออกจาก สิ่งที่วัดได้จริง — 4 ข้อที่พบใหม่ในรอบสำรวจนี้

5.1 · BOLA Guard ไม่ได้อยู่ใน request path จริง

ที่เคยอ้าง: แผนภาพ request lifecycle บนเว็บนี้เองแสดง "BOLA Guard" เป็นขั้นตอนหนึ่งของการตรวจ traffic ต่อจาก ModSecurity

ที่เป็นจริง: bola_guard.py (684 บรรทัด) ถูก import เฉพาะใน api/rules.py เท่านั้น เปิดเป็น endpoint 5 ตัว (CRUD policy 4 + POST /api/rules/bola/inspect ที่ต้องเรียกเองเพื่อตรวจ request ที่ส่งไปให้) และ main.py มี middleware แค่ CORSMiddleware ตัวเดียว — ไม่มี BOLA middleware

สรุป: BOLA Guard เป็น เครื่องมือตรวจแบบเรียกเอง (on-demand analysis tool) ไม่ใช่ยามที่ยืนเฝ้า traffic — traffic ที่วิ่งผ่านระบบตอนนี้ไม่ได้ถูก BOLA Guard ตรวจเลย ตัวโค้ดข้างในเขียนดีจริง (verify JWT, canonicalize path, anti-spoof header) แต่ต้องอธิบายให้ตรง ถ้าพูดตอน defense ว่า "traffic ทุก request ผ่าน BOLA Guard" จะถูกจับได้ทันที

5.2 · Caddy ออกใบรับรอง TLS ให้โดเมนอะไรก็ได้

Caddyfile ตั้ง on-demand TLS ว่า ask http://172.18.0.1:8000/api/health แต่ /api/health ตอบ 200 เสมอไม่ว่าถามถึงโดเมนอะไร — ทดสอบด้วย ?domain=evil-attacker.example ก็ได้ 200

ผลที่ตามมา: ใครก็ตามที่ชี้ DNS ของโดเมนตัวเองมาที่ IP ของ Main จะได้ใบรับรอง Let's Encrypt ออกให้อัตโนมัติ เสี่ยงโดน abuse จนชน rate limit ของ Let's Encrypt ซึ่งจะทำให้โดเมนจริงของเราออก/ต่ออายุ cert ไม่ได้

ของที่ควรใช้มีอยู่แล้วแต่ไม่ได้ต่อสาย: GET /api/domains/check-ssl-allowed?domain=... ตรวจจริงว่าโดเมนลงทะเบียนในตาราง waf_domains ไหม — นี่คือ endpoint ที่ ask ควรชี้ไปหา แก้ได้ด้วยการเปลี่ยน 1 บรรทัด

5.3 · vampi ไม่ถูก rate limit

server block ของ vampi ขาด auth_request ที่อีก 3 โดเมนมี (นับได้ 0) → request เข้า vampi ไม่ผ่านการตรวจ rate limit น่าจะตกหล่นตอนเพิ่ม server block ใหม่สำหรับ custom tunnel

5.4 · dns_verification_worker.py เป็น dead code

ไล่ import ทั้ง repo แล้ว ไม่ถูก import จากที่ไหนเลย ยืนยันซ้ำผลเดิมจากหน้า 11 — การ verify DNS ต้องกดเองผ่าน POST /api/domains/{id}/verify

§6 สถานะจริง ณ ตอนสำรวจ

ฝั่ง Main: ปกติทุกอย่าง

รายการสถานะ

Backend /api/health{"dynamodb":"connected","clickhouse":"connected"}

ฝั่ง origin ปลายทาง: หลุดการเชื่อมต่อทั้งหมด

โดเมนผลจริงสาเหตุ
dvwa404FRP: no route found — ไม่มี client ต่ออยู่
juice404FRP: no route found

การตรวจสอบที่ต้องระวัง — HTTP 200 ที่หลอกตา

ตอนยิงทดสอบครั้งแรก vampi ตอบ 200 พร้อมเนื้อหา VAmPI จริง ดูเหมือนใช้งานได้ปกติ แต่พอยิงซ้ำแบบ cache-busting พบว่า x-cache-status: MISS → 502 และ BYPASS → 502

200 ที่เห็นตอนแรกคือ cache เก่าที่ Edge เก็บไว้ ไม่ใช่ origin ที่ยังมีชีวิต — บทเรียนเดิมซ้ำอีกครั้ง เหมือนกรณี systemctl is-active ที่บอกว่า process ยังอยู่แต่ไม่ได้บอกว่าทำงานสำเร็จ คราวนี้คือ HTTP 200 ที่ไม่ได้แปลว่า origin ยังมีชีวิต ต้องยิงแบบ cache-bust ทุกครั้งเวลาตรวจสุขภาพ origin จริง

สาเหตุรากอยู่ฝั่ง Lab ไม่ใช่ Main — agent ทั้ง FRP และ cloudwaf บน Lab ไม่ได้ต่อเข้ามา (รูปแบบเดียวกับตอน KKU NAC session หมดอายุ) ทั้งสอง service ตั้ง Restart=always ไว้แล้ว น่าจะต่อกลับเองเมื่อเครือข่ายฝั่ง Lab กลับมา

§7 สรุปสำหรับตอบตอน defense

ประโยคที่ป้องกันได้จริง

"เครื่อง Main ทำหน้าที่เป็น control plane + data plane + intelligence plane พร้อมกัน มี backend 98 endpoint, ตรวจจับด้วย ModSecurity CRS ที่พิสูจน์ได้ว่าบล็อก SQLi ได้จริงทั้ง 4 โดเมน, มี rate limiting ที่ทำงาน inline บน traffic จริงผ่านกลไก nginx auth_request + Redis sliding window แบบ atomic, และมี ML ที่อธิบายผลได้ระดับ per-request ด้วย feature attribution ที่พิสูจน์ความถูกต้องทางคณิตศาสตร์ได้"

ข้อจำกัดที่ต้องพูดเอง อย่ารอให้ถูกจับได้

1. กฎ custom ทั้ง 6 ข้อเป็นระดับ demo — การตรวจจับจริงมาจาก CRS ล้วน · 2. ML recall แค่ 62.26% จึงยังไม่เปิด auto-block (มีหลักฐานสดว่าระบบเสนอกฎขยะจริง) · 3. BOLA Guard เป็น analysis tool ไม่ใช่ inline guard · 4. CDN multi-region ยังไม่เคย deploy จริง มี edge จริงแค่ 1 ตัว · 5. on-demand TLS ยังออกใบรับรองให้โดเมนใดก็ได้

§8 ข้อเสนอลำดับถัดไป (เฉพาะเครื่อง Main)

ลำดับงานเหตุผลความเสี่ยง
1ชี้ on_demand_tls ask ไปที่ /api/domains/check-ssl-allowedปิดช่องออก cert ให้โดเมนแปลกปลอม กัน Let's Encrypt rate limitต่ำ — แก้ 1 บรรทัด
2เพิ่ม auth_request ให้ block ของ vampiให้ทุกโดเมนถูก rate limit เหมือนกันต่ำ
3แก้คำอธิบาย BOLA Guard ให้ตรงว่าเป็น analysis toolกันโดนจับได้ตอน defenseไม่มี
4ต่อสาย dns_verification_worker เข้า startupโค้ดเขียนเสร็จแล้ว เหลือแค่เชื่อม ROI สูงต่ำ-กลาง
5เขียน custom rule ที่มีความหมายจริง โดยใช้ Blast Radius ทดสอบก่อนตอบคำถาม "กฎของคุณเองมีอะไรบ้าง" ได้กลาง — ต้องทดสอบ FP ก่อน

ไม่แนะนำให้ทำตอนนี้: ยกระดับ ML accuracy (เลื่อนหลังสอบจบ) และ production hardening เต็มรูป (mTLS, secret management) ซึ่งอยู่นอก scope โปรเจกต์นี้
