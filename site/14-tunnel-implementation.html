14 · PRIVATE TUNNEL — 30 ส.ค. 2026

FRP กลับมาแล้ว + เขียน private tunnel ของตัวเองใหม่ทั้งหมด

ต่อจากหน้า 13 — บทเรียนสำคัญ: audit เดิมสรุป root cause ของ tunnel ที่ตายผิด เพราะตรวจจากอาการภายนอกด้านเดียว พอเข้า Lab node ได้จริงถึงเจอสาเหตุแท้จริง แล้วใช้โอกาสนี้เขียน tunnel ใหม่ที่แก้ปัญหาเชิงสถาปัตยกรรม 7 ข้อของโค้ดเดิมไปด้วย

ผลรวม tunnel test 31/31 ผ่าน + smoke test เดิม 22 invariants/6 gates ไม่มี regression โค้ดใหม่ 795 บรรทัด Python stdlib ล้วน ไม่ใช้ tunnel library ใดๆ

§1 สรุปสถานะ: ก่อน vs หลัง

ก่อนหลัง
FRP tunnelclient 0 ราย, ทุก origin 404✅ ทำงาน — dvwa + juice ผ่าน tunnel จริง
Custom tunnelโค้ดมีแต่ deploy ไม่ได้ (7 เหตุผล — ดู §3)✅ ทำงานจริง — vampi ผ่าน tunnel ที่เขียนเอง

§2 ค้นพบสำคัญ: ทำไม FRP ถึงตายจริงๆ

บทเรียนเรื่อง root cause

หน้า 11 สรุปว่า tunnel ตายเพราะ network path ถูกบล็อก — ไม่จริง log บน Lab node บอกคนละเรื่อง: token in login doesn't match token from configuration — agent ต่อถึง Main:7000 ได้ตลอด สิ่งที่ล้มคือ authentication เพราะ token คนละตัว (หมุนไปตอน T5) audit ตอนนั้นเข้า Lab ไม่ได้จึงสรุปจากอาการภายนอกด้านเดียว — อย่าสรุป root cause จากหลักฐานฝั่งเดียว

แก้โดยอัปเดต token บน agent ให้ตรงกับที่หมุนใหม่ตอน T5 แล้ว restart — ผลทันที: agent login สำเร็จ, proxy ทั้ง 2 ตัว (dvwa, juice) start success, clients=1 จากนั้นย้อน T3 กลับไปใช้ tunnel จริงตามสถาปัตยกรรมที่ออกแบบไว้ (ยืนยันว่ามาจาก Lab จริงเพราะหน้า title ต่างกันจากตอนใช้ทางสำรอง)

§3 ทำไม custom tunnel เดิมใช้ไม่ได้ — 7 เหตุผล

§4 สถาปัตยกรรมใหม่

4.1 เปลี่ยนจาก port-based เป็น hostname-based

เดิม: 1 origin = 1 port บน WAF → ชนกัน + nginx route ไม่ได้ · ใหม่: ทุก origin ใช้ port เดียว (8060) แล้ว tunnel server อ่าน Host: header เพื่อเลือก agent — วิธีเดียวกับที่ FRP vhost ทำ ทำให้ nginx route ตาม server_name ได้ปกติ และ traffic ผ่าน ModSecurity ก่อนเสมอ

ผู้ใช้ทั่วไป
   │ HTTPS
   ↓
Caddy — TLS termination (Let's Encrypt / ZeroSSL)
   ↓
waf-nginx — ModSecurity v3 + OWASP CRS 3.3.10 (936 rules) + custom rules
   │          ← จุดที่ SQLi/XSS/traversal/RCE โดนบล็อก 403
   ↓ เลือกตาม server_name
   ├── frp_tunnel_router (172.18.0.1:8085) ── FRP ──┐
   └── cloudwaf_tunnel  (172.18.0.1:8060) ── ของเรา ─┤
                                                     ↓ TLS tunnel ที่ agent เปิดค้าง
                                              agent บน Lab (หลัง NAT ของ KKU)
                                                     ↓
                                              เว็บจริง (127.0.0.1:port)
agent เป็นฝ่ายต่อออก → เครื่อง origin ไม่ต้องเปิด inbound port, ไม่ต้องมี public IP, ไม่ต้องแก้ NAT

4.2 Credential model — จุดต่างหลักจาก FRP

FRPของเรา
รูปแบบshared token ตัวเดียวทั้งระบบcwt_<origin_id>_<secret> แยกต่อ origin
เก็บยังไงplaintext ในไฟล์ configเฉพาะ SHA-256 ของ secret
เทียบยังไงstring comparehmac.compare_digest
ขอบเขตทุก domainผูกกับ domain ที่อนุญาตเท่านั้น
ถ้าหลุดกระทบทุก originกระทบ origin เดียว

4.4 แก้ปัญหาทั้ง 7 ข้อจาก §3 ยังไง

  • token = origin UUID → credential แยกต่อ origin, เก็บเฉพาะ hash, ผูกกับ domain
  • host hardcode → อ่านจาก config/env
  • ไม่มี TLS → TLS 1.2+ พร้อม certificate pinning — agent ปฏิเสธไม่ยอมสตาร์ทถ้าไม่มีทั้ง pin และ CA verification
  • port ชนกัน → routing ด้วย hostname ใช้ port เดียว ไม่มีทางชน
  • ไม่มีอะไร route ไปหา → nginx server_name → upstream ผ่าน ModSecurity ก่อนเสมอ
  • ไม่ reconnect → loop + exponential backoff 2→60 วินาที, keepalive PING/PONG ทุก 30 วินาที
  • โค้ดเปราะ → import ปกติ, ไม่ log token, bound payload ก่อน allocate, lock ป้องกัน frame interleave

เพิ่มเติมที่ไม่ได้อยู่ใน 7 ข้อเดิม: verifier ล่ม = ปฏิเสธ ไม่ใช่ปล่อยผ่าน (fail closed) · ทุก error ของ verify คืน 401 เหมือนกันหมด (ป้องกัน probe หา origin ที่มีอยู่) · idle timeout 90 วินาที · vhost listener bind เฉพาะ docker bridge ไม่เปิดสู่อินเทอร์เน็ต

§7 ยังเหลือ

พบใหม่จากการเข้า Lab ได้ — ยังไม่ปิด

Lab มี Cloudflare tunnel 2 ตัวรันอยู่ — dvwa-tunnel.service ("DVWA Cloudflare Public Tunnel & CDN Edge") และ waf-tunnel.service ("WAF Lab Multi-Origin Public Tunnels") นี่คือ WAF bypass ที่หน้า 11 เตือนไว้ ยืนยันแล้วว่ามีจริง — เปิดเว็บทดสอบสู่อินเทอร์เน็ตตรงๆ โดยไม่ผ่าน ModSecurity ยังไม่ได้ปิดในรอบนี้เพราะยังไม่ได้ตรวจว่ามีอะไรพึ่งพาอยู่ — เป็น priority สูงสุดของโปรเจกต์ที่ยังค้างอยู่

§8 คุณค่าเชิง thesis

ประโยคที่ป้องกันได้ตอน defense

"ระบบมี private tunnel ที่พัฒนาเอง ให้เว็บที่อยู่หลัง NAT เข้าระบบป้องกันได้โดยไม่ต้องเปิดพอร์ต ใช้ credential แยกต่อ origin เข้ารหัสด้วย TLS พร้อม certificate pinning และ traffic ยังผ่าน WAF ครบทุก request — พิสูจน์ด้วยชุดทดสอบ 31 เคสที่รันกับระบบจริง"

ข้อจำกัดที่ต้องพูดตรงๆ: ยังไม่รองรับ WebSocket, cert เป็น self-signed (ใช้ pinning ทดแทน), ทดสอบกับ agent 1 ตัว ยังไม่ได้ทดสอบ scale หลาย agent พร้อมกัน
