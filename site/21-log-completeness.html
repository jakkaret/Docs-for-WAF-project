21 · LOG COMPLETENESS — 4 ก.ย. 2026

ข้อมูล log ครบไหม มากเกินไปไหม — ตรวจจาก artifact จริงทุกชั้น

ตรวจ schema จริงจาก ClickHouse, นับ population rate ของทุก field, อ่าน config ModSecurity/nginx ในคอนเทนเนอร์ที่รันอยู่, ไล่โค้ด ingestion pipeline จนถึงจุดที่ field หายไป — ไม่ได้เดาจากเอกสารเก่า

คำตอบสั้น ไม่ครบในหลายจุด และมากเกินจำเป็นในจุดเดียวที่ชัดมาก ข้อมูลจริง access_logs 175,084 แถว · audit.json 319 MB

§1 สรุปสำหรับผู้บริหาร

คำถามคำตอบ
ครบถ้วนไหม?ไม่ครบ มี field ที่ nginx จับได้จริงแต่หายก่อนถึง ClickHouse (referer, ssl info, body size) และ field ที่มีอยู่แต่ค่าใช้ไม่ได้จริง (request_time_ms เป็น 0 ถึง 68%, edge_node ผิดค่าจริง 72%)
มากเกินจำเป็นไหม?มากเกินในจุดเดียวที่ชัดมาก ModSecurity บันทึก request+response body ของทุก request ทุกสถานะ ลงไฟล์เดียวไม่มี rotation — ตอนนี้ 319 MB และโตต่อเนื่องไม่มีเพดาน
สาเหตุหลักมี ingestion pipeline คู่ขนาน 2 เส้นทาง ที่ map field ไม่เหมือนกัน — เส้นทางหนึ่งใส่ edge_node/request_time ถูก อีกเส้นทางไม่ใส่เลย ตกไปใช้ default ที่เขียนผิดไว้

§2 Schema จริงที่ dashboard ใช้อยู่

CREATE TABLE default.access_logs
(
    `id` UUID, `timestamp` DateTime, `client_ip` String, `method` String,
    `url` String, `status_code` UInt16, `request_time_ms` Float32,
    `user_agent` String, `country` String, `edge_node` String,
    `alert` UInt8, `attack_type` String, `rule_id` String
)
ENGINE = MergeTree ORDER BY (timestamp, client_ip)
13 คอลัมน์ · ไม่มี TTL clause เลย (เก็บถาวรไม่มีเพดาน) · ข้อมูลตั้งแต่ 20 ส.ค. ถึงปัจจุบัน 175,084 แถว

ที่ไม่มีเลยแต่ควรมีสำหรับ WAF analytics จริงจัง: request_id (ไว้ correlate กับ audit log), http_referer, response_size, ssl_protocol/ssl_cipher, และ origin_id/tenant_id — ตอนนี้แยก tenant ด้วยการ pattern-match บน url/client_ip เท่านั้น ไม่มี foreign key ตรง ๆ

§3 ตกหล่น — ข้อมูลถูกดึงมาแล้ว แต่ถูกทิ้งตอน insert

nginx log_format json_combined จับ field เหล่านี้จริง: request_id, remote_addr, request, status, body_bytes_sent, http_referer, http_user_agent, request_time, ssl_protocol, ssl_cipher

แต่ clickhouse_service.py ตอน insert ไม่ใส่ referer / body_bytes_sent / ssl_* ลง row เลย เพราะ schema ไม่มีคอลัมน์รองรับ — ข้อมูลถูกดึงมาแล้วแต่ตกหล่นตอนเขียน

ข่าวดีที่ต้องพูดให้ครบ

DynamoDB (save_log()) เก็บ event dict ทั้งก้อนแบบ schemaless ไม่ตัดทิ้ง — แปลว่าข้อมูลพวกนี้ ยังไม่หายไปจริง แค่ไม่อยู่ในตัวที่ dashboard ใช้ query/ทำกราฟ (ClickHouse) เท่านั้น เป็นปัญหาเรื่อง "เอามาใช้ไม่ได้" มากกว่า "หายตลอดกาล"

§4 ผิด — field ที่มีอยู่แต่ค่าใช้การไม่ได้

4.1 · edge_node ผิดค่าจริง 71.9%ยังไม่แก้
SELECT edge_node, count() FROM access_logs GROUP BY edge_node
→ sg       125,850   (71.9%)
→ edge-th   49,233   (28.1%)

ระบบมี Edge node จริงแค่ 1 ตัว (ประเทศไทย) — ไม่มี Singapore edge เลย แต่ 71.9% ของ log ถูก tag ว่า "sg"

Root cause: data.get('edge_node') or 'sg' — hardcode fallback เป็น 'sg' ทุกครั้งที่ upstream ไม่ส่งมา และเส้นทางที่ Main อ่าน log ตัวเอง (log_forward.py) ไม่เคยใส่ edge_node เลย จึงตกไปโดน default ผิดทุกครั้ง

ผลกระทบ: กราฟ/รายงานที่ break down ตาม edge node ผิดทันที — บอกว่า 72% ของ traffic มาจาก edge ที่ไม่มีอยู่จริง

แถมอีกชั้น: DynamoDB มี "Edge-TH" กับ "edge-th" ปนกัน — รวมทั้งระบบมีอย่างน้อย 3 รูปแบบสตริงสำหรับ node เดียวกัน (sg, edge-th, Edge-TH) ไม่มี canonical value เลย

4.2 · request_time_ms เป็น 0 ถึง 68.4%ยังไม่แก้
119,765 zero | 55,318 nonzero | 175,083 total

nginx จับ $request_time จริงในทุก request แต่ normalize_access() ไม่ดึงค่านี้มาเลย จึงตกไปใช้ default 0.0

ผลกระทบที่ต้องระวังที่สุด: ตัวเลข latency เฉลี่ยที่ dashboard และ AI Copilot อ้างอิงคำนวณจากข้อมูลที่ 68% เป็นศูนย์ปลอม — ค่าเฉลี่ยที่ได้ต่ำกว่าความจริงมาก ห้ามเชื่อตัวเลขนี้จนกว่าจะแก้

§5 มากเกินจำเป็น — ModSecurity audit log

SecAuditEngine On
SecAuditLogRelevantStatus ".*"      ← ทุกสถานะ ไม่ใช่แค่ที่ถูกบล็อก
SecAuditLogParts ABIJDEFHZ           ← "I"/"E" = request+response body เต็ม
SecAuditLogType Serial
SecAuditLog /var/log/modsecurity/audit.json
config จริงที่รันอยู่ในคอนเทนเนอร์ waf-nginx

".*" = จับทุกสถานะ (200 ก็โดน) รวมกับ Parts ที่มี body ทั้ง 2 ทิศทาง = บันทึก body เต็มของทุก request ที่เข้าระบบ ไม่ใช่แค่ตัวที่ถูกบล็อก

319 MBไฟล์เดียว ใน 15 วัน
~21 MBโตต่อวัน
~7.7 GBประมาณการต่อปี บน host เดียว
0logrotate config ที่มี
ทำไมนี่คือ "เกินจำเป็น" ไม่ใช่แค่ "เยอะ"

การบันทึก body เต็มของ traffic ปกติ (status 200) ไม่มีประโยชน์เชิงความปลอดภัยเพิ่มจากที่ ClickHouse บันทึกไว้แล้ว (URL/method/status) — สิ่งที่มีค่าจริงคือ body ของ request ที่ ถูกบล็อกหรือ flag เท่านั้น ตอนนี้เก็บทุกอย่างปนกัน ทั้งเปลืองพื้นที่และเพิ่มความเสี่ยง privacy/PDPA (ตรงกับที่หน้า 12 T14 เตือนไว้แล้ว — ยืนยันว่ายังไม่แก้)

ไม่มี retention/TTL ที่ชั้นไหนเลย — ClickHouse ไม่มี TTL clause · DynamoDB ไม่มี TTL attribute · ModSecurity audit log ไม่มี rotation — ทั้ง 3 ชั้นเก็บถาวรไม่มีเพดานเหมือนกันหมด

/root/waf_project/logs/               397 MB
  ├── modsecurity/audit.json          319 MB  (ทุก request ทุกสถานะ มี body)
  └── nginx/                           46 MB  (access log ปกติ)

§6 Root cause ที่แท้จริง — ไม่ใช่บั๊กเดี่ยว ๆ 5 จุด

ทั้งหมดเป็นรูปแบบเดียวที่เกิดซ้ำ: ระบบมี ingestion pipeline คู่ขนาน 2 เส้นทางที่ไม่ได้ทำให้ field mapping ตรงกัน

เส้นทางไฟล์edge_noderequest_time
Edge → Main (HTTP push)cdn_log_forward.py✅ ใส่ถูก✅ ใส่
Main อ่าน log ตัวเองlog_forward.py❌ ไม่ใส่เลย❌ ไม่ใส่เลย
บทเรียนที่สำคัญกว่าตัวบั๊ก

ทั้งสองเส้นทางเรียก save_log() ตัวเดียวกัน ซึ่งมี default fallback ที่เดาค่าแทนที่จะบอกว่าไม่รู้ — เมื่อ default ผิด ทุกครั้งที่ pipeline ที่สองทำงาน ข้อมูลจะผิด โดยไม่มีใครรู้ เพราะไม่มี error ปรากฏที่ไหนเลย การเดาเงียบ ๆ อันตรายกว่าการ fail ดัง ๆ

§7 แนวทางแก้ เรียงตามความคุ้ม

#งานทำอะไรความเสี่ยง
1แก้ default 'sg'เปลี่ยนเป็น 'unknown' + log warning ว่าเส้นทางไหนไม่ส่งมา — เลิกเดาเงียบ ๆแทบไม่มี
2เติม request_time/edge_nodeให้ normalize_access() ดึงค่าที่ nginx จับไว้แล้วมาใช้จริง (request_time เป็นวินาที ต้อง ×1000)ต่ำ
3เพิ่มคอลัมน์ที่ขาดhttp_referer, request_id, body_bytes_sent เข้า schema ClickHouseกลาง — แก้ schema
4ลดขอบเขต audit logSecAuditLogRelevantStatus "^(?:5|4[03])" — เก็บเฉพาะที่ถูกบล็อก/errorกลาง — กระทบ forensics
5ใส่ TTL/rotation ทั้ง 3 ชั้นlogrotate + ClickHouse TTL + DynamoDB TTL attributeกลาง
6canonical edge_nodeenum เดียวทั้งระบบ เลิกมี 3 รูปแบบสตริงต่ำ

ข้อ 1-2 คือจุดที่ควรทำก่อน — ต้นทุนต่ำมาก (แก้ไม่กี่บรรทัด) แต่ปิดปัญหาที่ทำให้ ตัวเลขบน dashboard ผิดอยู่ตอนนี้ ซึ่งเป็นความเสี่ยงตรงกับกฎของโปรเจกต์เรื่อง "แยก vendor claim ออกจาก measured ground truth"
