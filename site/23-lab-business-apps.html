23 · LAB NODE & BUSINESS APPS — 6 ก.ย. 2026

Lab node เพิ่มเว็บธุรกิจสมจริง 3 ตัว — แต่ยังไม่ได้ต่อเข้า WAF

เดิม Lab เป็น testbed เว็บช่องโหว่ล้วน (DVWA, Juice Shop, vAmPI, bWAPP) ตอนนี้เพิ่มเว็บธุรกิจที่เขียนขึ้นใหม่อีก 3 ตัวให้เหมือนระบบ production จริง — ทำให้ traffic ที่ใช้ทดสอบใกล้เคียงของจริงมากขึ้น

เว็บบน Lab ตอนนี้ 7 ตัว (ช่องโหว่ 4 + ธุรกิจจริง 3) ตรวจแล้ว ทั้ง 3 ตัวใหม่ยังไม่ถูก route ผ่าน WAF

§1 ทำไมการเพิ่ม 3 เว็บนี้ถึงสำคัญกับ thesis

ข้อจำกัดเดิมของ testbed คือ เว็บทั้ง 4 ตัวเป็นแอปช่องโหว่โดยตั้งใจ (DVWA, Juice Shop, vAmPI, bWAPP) ซึ่งดีสำหรับทดสอบว่า WAF จับการโจมตีได้ไหม แต่ไม่สะท้อน traffic ของเว็บธุรกิจจริง

การมีเว็บธุรกิจที่มี business logic จริง (ตะกร้าสินค้า, จองคิวแพทย์, สมัครแพ็กเกจ SaaS) ทำให้ทดสอบสิ่งที่เดิมทดสอบไม่ได้:

  • False positive กับ traffic ปกติ — เว็บช่องโหว่ไม่มี traffic ปกติที่ซับซ้อนพอ ส่วนการ checkout/จองคิวมีทั้ง form, JSON body, และอักขระพิเศษในชื่อ/ที่อยู่จริง
  • Blast Radius Simulator มีข้อมูลจริงให้ replay — กฎใหม่ที่เขียนจะทดสอบกับ traffic ที่เหมือนของจริงได้
  • ตอบคำถาม "ระบบนี้ใช้กับเว็บจริงได้ไหม" ได้ดีขึ้น — เดิมตอบได้แค่ "ใช้กับ DVWA ได้"

§5 ตรวจของจริง — ทั้ง 3 ตัวยังไม่ถูกต่อเข้า WAF

ผลตรวจบนเครื่อง Main จริง 6 ก.ย. 2026

รายงานระบุว่าเว็บทั้ง 3 สร้างขึ้น "เพื่อใช้เชื่อมต่อไปยัง WAF / Reverse Proxy / CDN" — ตรวจแล้วพบว่ายังไม่ได้เชื่อมจริงเลยสักตัว

สิ่งที่ตรวจผล
server_name ใน nginx templateไม่มี มีแค่ juice, dvwa, vampi, bwapp
upstream ที่ชี้ไปพอร์ต 8001-8003ไม่มี มีแค่ frp_tunnel_router, cloudwaf_tunnel, dvwa_backend
โดเมนใน Caddyfileไม่มี มี 8 โดเมนเดิมเท่านั้น
origin ที่ลงทะเบียนใน DynamoDBไม่มี ไม่มี origin สำหรับ 3 เว็บใหม่
tunnel_domains ของ agentไม่มี มีแค่ 4 โดเมนเดิม

แปลว่าอะไร: เว็บทั้ง 3 เข้าถึงได้เฉพาะทาง http://10.198.200.75:800X ตรง ๆ ผ่าน KKU VPN — traffic ไม่ผ่าน ModSecurity เลย ยังไม่ใช่ช่องโหว่สู่อินเทอร์เน็ต (เพราะ Lab ไม่มี public IP) แต่เป็นรูปแบบเดียวกับข้อสังเกตเดิมในหน้า 07 เรื่องพอร์ตแอปทดสอบที่เปิดตรงจาก host

งานที่เหลือถ้าจะต่อจริง: สร้าง origin + ออก tunnel token → เพิ่มโดเมนใน Caddy → เพิ่ม server_name block ใน nginx ที่ proxy ไป tunnel → ตรวจว่า SQLi โดน 403 และ traffic ปกติผ่านได้ (ปัญหาเดียวกับที่ต้องแก้ 3 ที่ด้วยมือ ตามที่บันทึกไว้เรื่อง single source of truth)

§6 เหตุขัดข้องที่พบระหว่างตรวจ — tunnel ตายอยู่ตอนนี้

พบสด 6 ก.ย. 2026 — ทั้ง 4 โดเมนเดิมเข้าไม่ได้

ยิงทดสอบแบบ cache-bust: dvwa 000 · juice 000 · vampi 502 · bwapp 000 — ไม่มีโดเมนไหนใช้งานได้เลย

Root cause ที่ยืนยันแล้ว — คนละสาเหตุกัน 2 ชั้น

1 · custom tunnel — origin ถูก archive401 ทุกครั้ง

agent บน Lab ยังมีชีวิตและพยายามต่อกลับตลอด (เห็น request เข้ามาทุก ~20 วินาที) แต่ /api/tunnel/verify-agent ตอบ 401 Unauthorized ทุกครั้ง

ตรวจ origin ในฐานข้อมูลพบ: origin Lab Multi-App (private tunnel) มี tunnel_token_hash ครบ · tunnel_domains ครบทั้ง 4 โดเมน · แต่ status = archived

โค้ด verify_agent ปฏิเสธ origin ที่ archived โดยตรง — token ยังถูก แต่ถูกปฏิเสธเพราะสถานะ

นี่คือความเสี่ยงที่เราทำนายไว้แล้ว และมันเกิดขึ้นจริง

ตอนวิเคราะห์เรื่อง "ไม่มีปุ่มตัดการเชื่อม tunnel" เราบันทึกไว้ว่า การกด Archive Origin จะตัด tunnel จริงแต่ "เชือดทั้งต้น" เพราะ verify-agent เช็ค status == archived — ตอนนี้เกิดขึ้นแล้วจริง ๆ และมันเงียบมาก ไม่มี error แจ้งว่าเว็บ 4 ตัวจะดับตาม

วิธีแก้: restore origin กลับ (POST /api/origins/{id}/restore) แล้ว agent จะต่อกลับเองเพราะตั้ง Restart=always ไว้

2 · FRP — token ไม่ตรงAuthentication failed

log ของ frps ขึ้นซ้ำ ๆ: new proxy [juice/dvwa/bwapp-waf-it-kku-online] error: Authentication failed: Invalid or expired WAF Tunnel Token

เป็นอาการเดียวกับที่เคยเจอตอนหมุน token ใน T5 แล้วลืมอัปเดตฝั่ง agent — บทเรียนในหน้า 14 ว่า "อย่าสรุป root cause จากหลักฐานฝั่งเดียว" ใช้ได้อีกครั้ง

บทเรียนที่ควรบันทึก: ระบบไม่มีการแจ้งเตือนเมื่อ tunnel ตาย — ต้องมีคนไปเปิดดูเองถึงจะรู้ ทั้งที่ /api/tunnel/status รู้ว่า agent_count = 0 อยู่แล้ว นี่คือช่องว่างที่ n8n monitoring (หน้า 22) จะปิดได้ตรงจุด
