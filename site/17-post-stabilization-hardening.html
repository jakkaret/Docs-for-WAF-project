§2 ปิด Cloudflare Tunnel bypass — priority สูงสุด

P0 ตาม CLAUDE.md — ปิดแล้ว

หน้า 14 เตือนไว้ว่า Lab มี dvwa-tunnel.service และ waf-tunnel.service รัน cloudflared ชี้ตรงเข้า origin port (80, 3000, 8080, 5000, 8081) — ข้าม ModSecurity ทั้งหมด ตอนนี้ปิดถาวรแล้วด้วย systemctl disable --now ทั้งคู่

แก้ความเข้าใจผิดของตัวเองระหว่างทาง — รอบแรกสรุปจาก systemctl is-active = active running ว่า bypass "เปิดรั่วอยู่จริง" ซึ่งผิด ตรวจลึกแล้วพบว่า process ยังอยู่มา 7 วันแต่ต่อ Cloudflare ไม่ติดเลย:

cloudflared processes : 6 ตัว รันมา 7 วัน
TCP connections       : 0
UDP/QUIC connections  : 0
DNS ของ URL ที่บันทึก  : ไม่ resolve (ยืนยันผ่าน 1.1.1.1 และ 8.8.8.8)
น่าจะเพราะ KKU VPN บล็อก outbound ตอนนั้น — จึงยังไม่มีใครเข้าถึงได้จริง แต่ตั้ง Restart=always + enabled แปลว่าเน็ตกลับมาปกติเมื่อไหร่ มันจะได้ URL ใหม่แล้วเปิดทางลัดทันที = ช่องโหว่ที่รออยู่ ไม่ใช่ช่องโหว่ที่กำลังรั่ว ณ ขณะนั้น — แต่ก็ยังต้องปิดอยู่ดี เพราะเงื่อนไขเปลี่ยนได้ทุกเมื่อ

บทเรียนซ้ำ: active running ของ systemd บอกว่า process ยังอยู่ ไม่ได้บอกว่ามันทำงานสำเร็จ — เจอบทเรียนเดียวกันนี้อีกครั้งใน §4

§3 RAM leak จริง — reload=True ในโปรดักชัน

ผู้ใช้ขอ "ระบบพื้นฐานทั้งหมดทำงานได้ปกติ...แก้ได้เลย...แจ้งตอนเสร็จหมด" — มอบอำนาจตัดสินใจให้เต็มที่ ระหว่างไล่ตรวจเจอ waf-dashboard.service รัน python main.py ตรง (ไม่ใช่ผ่าน uvicorn CLI) ซึ่งไปโดน uvicorn.run(..., reload=True) ที่ฝังอยู่ใน __main__ block

ทำไมอันตราย

Uvicorn reload mode สร้าง supervisor + worker process แยกกัน — worker (spawn child) กิน RSS 1.06 GB เดี่ยวๆ (27% ของ RAM ทั้งเครื่อง) ถาวรตลอดเวลาที่ service รัน และยังเฝ้าดู filesystem ตลอดเวลา — ถ้ามีไฟล์ .py ถูกเขียนระหว่าง deploy มันจะ auto-restart กลางคันโดยไม่ตั้งใจ ทำให้ deploy บางส่วนถูก serve ก่อนไฟล์ครบ (reload=True เป็น dev-only ตามเอกสาร Uvicorn เอง ไม่ควรอยู่ใน production)

แก้: ลบ reload=True, ออกจาก dashboard/backend/main.py บรรทัดเดียว, deploy, restart

2663→1626RAM ใช้บน Main (MB)
+1036MB ที่ว่างเพิ่มขึ้น

process เหลือตัวเดียว (ไม่มี spawn child อีก), smoke test 22+6 ผ่านเหมือนเดิม

§4 waf-nginx unhealthy 23 ชั่วโมง — สถานะผิด ไม่ใช่ WAF ล่ม

Root cause จากอ่านโค้ด /usr/local/bin/healthcheck จริง (ไม่เดา): script เป็นของ image ต้นทางที่ตรวจ https://localhost:${SSL_PORT}/healthz แต่ container นี้ไม่มี SSL listener เลย (TLS termination อยู่ที่ Caddy ชั้นนอก) → connect refused ทุกครั้ง ตลอด FailingStreak 2783

แก้: เพิ่ม healthcheck: override ใน docker-compose.yml ให้ตรวจ http://localhost:8080/healthz (endpoint จริงที่ทำงาน) แทน — ไม่แตะ nginx config ตัวจริงเลย เป็นแค่ metadata ของ Docker ยืนยันก่อนแก้ว่าไม่มีอะไรอ่านค่านี้ไปตัดสินใจ (depends_on แบบ list ธรรมดา ไม่มี condition: service_healthy, backend ก็ไม่อ่าน docker health) — เป็นแค่สถานะผิดที่ทำให้คนอ่าน docker ps เข้าใจผิดว่า WAF ล่ม ไม่เคยกระทบ traffic จริง

ผล: waf-nginx Up (healthy)

§5 bwapp เสิร์ฟผิดแอป → เจอ Lab หลุด KKU network authentication

เดิม bwapp.waf-it-kku.online ไม่มี server_name block ใน nginx เลย ตกไป default fallback → เสิร์ฟ container dvwa บน Main ผิดตัว — ตรวจแล้ว: bwapp ไม่เคยถูกต่อสายเข้าระบบเลยตั้งแต่แรก (ไม่มี origin ใน DynamoDB, ไม่มี FRP proxy, ไม่มี tunnel registration)

restart service ที่ถือ long-lived connection มีต้นทุนแฝง

ระหว่างต่อสาย (เพิ่ม FRP proxy + nginx block) ต้อง restart waf-agent.service — connection เดิมที่ทำงานอยู่ (dvwa, juice ผ่าน FRP) หลุดและต่อกลับไม่ได้ ลองย้ายไป custom tunnel แทนแล้ว restart cloudwaf-agent.service — connection เดิมของ vampi ก็หลุดตามไปด้วยเช่นกัน

วินิจฉัยจนพบสาเหตุจริง (ไม่ใช่สิ่งที่งานรอบนี้ทำให้เกิด):

ping Main            → "Destination Net Prohibited" จาก KKU VPN gateway เอง
port 80  → Main      → เชื่อมได้
port 443/7000/8050   → connection refused ทั้งหมด
port 443 → 1.1.1.1   → connection refused (host ภายนอกที่ไม่เกี่ยวกับระบบเลย)
curl http://neverssl.com → redirect ไป KKU NAC captive portal login
สรุป: Lab หลุดจาก KKU network authentication (NAC session หมดอายุ) — บล็อกทุกอย่างยกเว้น HTTP ธรรมดา เป็นปัญหาเดิมที่ซ่อนอยู่ (เหตุผลเดียวกับที่ cloudflared ใน §2 ต่อ Cloudflare ไม่ติด) connection เดิมรอดมาได้เพราะเป็น TCP session ที่เปิดค้างไว้นาน ไม่ต้องต่อใหม่ — พอ restart service ต้องขอ connection ใหม่ถึงเจอบล็อกที่ซ่อนอยู่

นี่คือ network-level authentication ที่ต้องใช้ credential ของผู้ใช้เอง (KKU account) ไม่ใช่สิ่งที่ทำผ่าน SSH ได้ — รอผู้ใช้ login ใหม่ที่เครื่อง Lab แล้ว restart agent ทั้งสองตัวต่อกลับติดทันที ยืนยันด้วย title/redirect ของแอปจริง ไม่ใช่แค่ status code:

§6 H4 · ClickHouse injection — ปิดครบ 6 จุด

ตรวจใหม่พบ 8 จุดที่ escape ด้วย .replace("'", "\\'") เดิม แบ่งได้ 2 กลุ่มจริง — 6 จุดเป็น ClickHouse SQL injection จริง (clickhouse_service.py ×3, analytics.py ×1, cdn.py ×1, logs.py ×1), อีก 2 จุดใน rule_manager.py ไม่ใช่ ClickHouse เลย (เขียนไฟล์ ModSecurity .conf คนละ sink คนละ trust model) — ไม่แตะตอนนั้น เพราะยังไม่ได้พิสูจน์ว่ากติกา escape เหมือนกันไหม บันทึกไว้เป็นรายการแยก (→ ดู §7 ที่ตามไปพิสูจน์และปิดจริง)

Root cause — พิสูจน์กับ ClickHouse จริงก่อนแก้

ClickHouse ตีความ \ เป็น escape character ในสตริง (แบบเดียวกับ MySQL) — โค้ดเดิม escape แค่ quote โดยไม่ escape backslash ที่มีอยู่ก่อนหน้า ทำให้ input ที่มี \ นำหน้า ' (เช่น x\' OR 1=1 --) หลุดออกจาก string literal ได้จริง — ยืนยันด้วยการรันจริง: escape เดิมทำให้ query error Unmatched parentheses (หลุดจริง), escape ใหม่ (backslash ก่อน แล้วค่อย quote) round-trip กลับเป็นสตริงเดิมเป๊ะ

แก้: เพิ่มฟังก์ชันกลาง escape_like_value() ใน services/clickhouse_service.py ใช้ร่วม 5 จุดที่เป็น LIKE-pattern fuzzy match — ส่วน logs.py explain-by-id (ค่าเดียว match ตรงตัว) เปลี่ยนเป็น parameterized query จริง ({log_id:String} + parameters=) ตาม pattern ที่ T6 (หน้า 13) วางไว้แล้ว — ดีกว่า escape เพราะไม่พึ่งการ escape ถูกต้องเลย

ทดสอบ: เทสใหม่ 3 ตัว (round-trip ผ่าน reference decoder จำลองกติกา unescape ของ ClickHouse เอง, ไม่มี unescaped quote หลุด, input ปกติไม่เปลี่ยน) ผ่านหมด 3/3 → full suite 58 passed (เดิม 55) deploy + verify กับของจริง: ยิง attack string เดียวกันเข้า 3 endpoint จริงผ่าน HTTP — ทุก endpoint ตอบ 200 ปกติ ไม่ 500 ไม่หลุด SQL

§7 ช่องโหว่ที่ 7 — SecRule injection ใน rule_manager.py (พบผ่าน TDD)

ไล่หา bug ทั้งระบบแบบกว้างๆ ด้วย TDD process จริง (RED→GREEN→verify) เลือกจุดที่ค้างไว้จาก §6 — สองจุดใน rule_manager.py หน้าตาเหมือน ClickHouse bug (escape แค่ quote ไม่ escape backslash ก่อน) แต่เป็นคนละ sink (เขียนไฟล์ ModSecurity .conf ไม่ใช่ ClickHouse)

ตรวจกติกาจริงก่อน: เอกสาร ModSecurity official ("Data Formats" wiki) ยืนยันว่า backslash เป็น escape character ใน quoted string เหมือน ClickHouse — สงสัยว่าเป็นบัคจริง

พิสูจน์กับเครื่องมือจริงก่อนเขียนโค้ดใดๆ

สร้าง rule message = pwned\' ctl:ruleRemoveById=900001 ด้วย escaping เดิม deploy เข้า custom-rules บน Main ชั่วคราว รัน nginx -t (แค่ตรวจ syntax ไม่ reload ไม่กระทบ traffic จริง) แล้วลบไฟล์ทันที — ได้: Expecting an action, got: ctl:ruleRemoveById=900001',tag:'end'

ยืนยันแล้วว่าเป็นช่องโหว่จริง ไม่ใช่แค่ทฤษฎี — admin (ที่ผ่าน RBAC มาแล้ว) ที่สร้าง custom rule สามารถ inject ModSecurity action เข้าไปในไฟล์ rule ได้ เช่น ctl:ruleRemoveById=<id> ปิดการทำงานของ rule อื่นแบบเงียบๆ ถ้า payload ถูกออกแบบให้ syntax ถูกต้อง (payload ทดสอบนี้ตั้งใจให้ error เพื่อพิสูจน์จุดที่หลุด ไม่ใช่ payload โจมตีจริงที่ผ่าน)

TDD: เขียนเทส 3 ตัวก่อนแก้โค้ด (tests/test_rule_secrule_escape.py) — round-trip ผ่าน reference decoder จำลองกติกา unescape ของ ModSecurity เอง ครอบคลุมทั้ง add_rule และ update_rule — รันแล้วเห็น FAIL จริงตามที่คาด ก่อนเริ่มแก้โค้ดสักบรรทัด

แก้: เพิ่ม escape_secrule_string(value, quote_char) (escape backslash ก่อน quote — เหมือน escape_like_value ของ §6 เป๊ะ) ใช้แทนทั้ง add_rule และ update_rule → เทสผ่านหมด 3/3, full suite 61 passed (เดิม 58)

พิสูจน์ซ้ำกับเครื่องมือจริง: เอา payload เดิม มาสร้างด้วย escaping ใหม่ deploy ทดสอบ + nginx -t อีกครั้ง → syntax is ok / test is successful — ปิดช่องโหว่จริง ไม่ใช่แค่ผ่าน unit test Deploy: restart waf-dashboard.service, สอบผ่าน smoke test 22+6, sanity check ว่า custom rule จริงที่มี backslash ใน regex operator ปกติ (เช่น \s+) ยังพาร์สผ่าน nginx -t เหมือนเดิม ไม่กระทบ

§8 FRP_ADMIN_PASS — ตัดสินใจคงไว้ตามเดิม

Ruling จากผู้ใช้ — accepted risk

เตรียม password ใหม่แล้ว (สุ่ม 32 ตัวอักษร) แต่ผู้ใช้ตัดสินใจไม่เปลี่ยน — เหตุผล: ตอนนี้ยังเป็นขั้นตอนพัฒนา (dev stage) ไม่ใช่ production จริง ยอมรับความเสี่ยงนี้ชั่วคราว ลบ password ที่ generate ไว้ทิ้งแล้วก่อนหน้านี้ ไม่มี artifact ค้าง

ไม่เผยค่า default ปัจจุบันบนหน้านี้ (ยังใช้งานอยู่จริง) — ตามนโยบายเดียวกับ credential อื่นบนไซต์นี้: บอกตำแหน่ง/ความเสี่ยง ไม่บอกค่าที่ยังใช้งานได้จริง

§9 T13 · แก้ตัวเลข ML ที่โฆษณาเกินจริง + README มืออาชีพ

ผู้ใช้ถามว่าใครเขียนเลข 93.40% ที่ README เดิมอ้าง — สืบจาก git log จริง: commit แรก (10 ส.ค.) เทรนโมเดลครั้งแรกได้ 93.40% จริงตอนนั้น เขียนลง README, commit ต่อมา (23 ส.ค.) เทรนใหม่ด้วย synthetic data generator ได้ผล eval ใหม่ = 80.47% แต่ README ไม่เคยอัปเดตตาม — สรุป: ไม่ใช่การโม้ตั้งแต่แรก แต่เป็นเอกสารตกยุคหลังโมเดลถูกเทรนใหม่

TDD แก้ที่ behavior จริงก่อน (ไม่ใช่แค่แก้ข้อความ)

/health endpoint เดิม hardcode accuracy_target_passed: True เสมอ ทั้งที่ eval_accuracy จริงอยู่ที่ 0.8047 (ต่ำกว่า target 0.85) — RED: เขียนเทส 4 ตัวก่อนมีฟังก์ชัน accuracy_meets_target() → ImportError ตามคาด · GREEN: เพิ่มฟังก์ชันจริง (fail-closed: ไม่มีข้อมูล = ไม่ผ่าน) ลบ fallback 0.934 ที่ยังอ้างเลขเก่าออกด้วย → เทสผ่าน 4/4, ml/tests รวม 18/18

Deploy จริงบน Main: accuracy_target_passed:true (ขัดแย้งในตัวเองกับ eval_accuracy 0.8047) → accuracy_target_passed:false, eval_accuracy:0.8047 ตรงความจริงแล้ว

กวาดเอกสาร/placeholder ที่เป็นข้อความ static ทั่วโปรเจกต์: README.md และแผนเทียบ Cloudflare (เลข 93.40%/0.9895 → 80.47%/0.8847 ทุกจุด รวม verdict "✅ เทียบเท่า" ที่ต้องแก้เป็น "⚠️ ยังต่ำกว่า target" เพราะอิงเลขเก่า) · train_model.py ที่ print "(Target > 85% PASSED!)" hardcode ไม่เช็คค่าจริง · dashboard HTML ที่มี placeholder ผิดทั้งชุด (train/test split, benign/attack totals, confusion matrix ทั้ง 4 ช่อง) ตรวจพบว่าไม่มี fallback reset ถ้า fetch ข้อมูลจริงล้มเหลว — โหมด fetch-fail จะโชว์เลขเก่าค้างอยู่ถ้าไม่แก้ placeholder ด้วย ยืนยันปิดครบด้วยการ grep เลขเก่าทั่ว repo หลังแก้ → ไม่เจอเหลือเลยสักจุด

เขียน README ใหม่ทั้งฉบับ (ผู้ใช้ขอเพิ่มระหว่างทาง) จากคู่มือ local setup อย่างเดียว เปลี่ยนเป็นโครงสร้าง README มืออาชีพ: ภาพรวม+เหตุผลออกแบบ, สถาปัตยกรรม 3 เครื่องพร้อม diagram, tech stack ตามเวอร์ชันจริงจาก package.json/requirements.txt, ผลทดสอบ ML เลขจริง, roadmap ที่บอกข้อจำกัดตรงๆ — ตัดลิงก์ไปไฟล์คู่มือที่อ้างถึงแต่ไม่มีอยู่จริงในโปรเจกต์ออกด้วย ไม่ใส่ลิงก์เสีย

§10 คุณค่าเชิง thesis

ประโยคที่ป้องกันได้ตอน defense

"ปิด WAF bypass ที่ระบุไว้เป็นความเสี่ยงสูงสุดของโปรเจกต์ได้จริงหลังพิสูจน์ด้วยข้อมูล network-level (DNS/TCP/UDP) ไม่ใช่แค่อ่านสถานะ systemd — และใช้ TDD (RED→GREEN→verify กับเครื่องมือจริง) หาช่องโหว่ inject เข้าไฟล์ config ที่ไม่มีใครเคยพิสูจน์มาก่อนจนเจอและปิดได้"

ข้อจำกัดที่ต้องพูดตรงๆ: FRP_ADMIN_PASS ยังเป็นค่า default อ่อน (ตัดสินใจรับความเสี่ยงไว้ระดับ dev stage) · หน้า Tunnels frontend ยังไม่รวมสถานะ tunnel ใหม่เข้ากับของเดิม · เหตุขัดข้องเครือข่ายของมหาวิทยาลัย (KKU NAC) เป็นความเสี่ยงภายนอกที่ทีมนี้ควบคุมไม่ได้ — บทเรียนคือต้องแยกให้ออกระหว่าง "ระบบพัง" กับ "โครงสร้างพื้นฐานภายนอกที่ระบบพึ่งพาไม่พร้อมใช้งานชั่วคราว"
